
1. Что такое Action в Aivion
Предлагаю зафиксировать:
Action — конкретное управленческое действие, которое Deep Analysis считает обоснованным Findings и доступными facts и которое пользователь может выполнить в отношении одного разрешённого Action Target.
У нас четыре Action Target:
ACCOUNT
LEAF_CATEGORY
SKU
CAMPAIGN
И только они.
Цепочка всегда:
Facts
↓
Finding
↓
Recommendation
↓
Action
Нельзя:
Facts
↓
Action
и тем более:
AI intuition
↓
Action

2. Recommendation и Action — не одно и то же
Например Deep пришёл к выводу:
Search у SKU ухудшился, но данные отстают на два дня и Funnel недоступен.
Это может дать:
Recommendation:
понаблюдать ещё несколько периодов
Но:
Action:
нет
Другой пример:
Текущий остаток SKU покрывает два дня спроса, открытого пополнения нет.
Recommendation:
Пополнить запас.
Action:
SKU_INCREASE_REPLENISHMENT
target = SKU 417
То есть Action создаётся только для Recommendation:
ACTIONABLE_NOW
Если Recommendation:
MONITOR
INSUFFICIENT_EVIDENCE
Action запрещён.

3. V1 остаётся полностью read-only
Это принципиально.
Даже если Ozon API технически позволяет менять что-либо, Aivion v1 ничего самостоятельно не меняет.
Action:
SKU_ADJUST_PRICE
recommended_price = 2190 ₽
означает:
Aivion рекомендует продавцу установить 2 190 ₽.
А не:
Aivion отправляет POST в Ozon.
Это отдельный будущий слой:
Action Recommendation
↓
User confirmation
↓
Fresh-state revalidation
↓
Execution Adapter
↓
Ozon write API
Причём Action из вчерашней Publication никогда нельзя будет просто отправить в Ozon сегодня без повторной проверки текущего состояния.

4. Почему taxonomy всё равно сверяем с Ozon API
Хотя v1 read-only, полезно не проектировать действия, которые вообще оторваны от реальных рычагов seller.
Текущий Seller API подтверждает наличие write-операций для изменения цены (/v1/product/import/prices) и FBS/rFBS stock quantity (/v2/products/stocks). Для FBO при этом существует отдельный полноценный supply workflow: создание draft/supply order, изменение состава заявки и работа с timeslot. То есть FBO replenishment и “обновить остаток” — принципиально разные действия, и будущий executor не должен смешивать их. GitHub
Текущие Ozon promotion API также позволяют добавлять/убирать товары из акций; отдельная beta-family seller actions умеет создавать/обновлять seller-managed акции и менять их активность. GitHub
Performance API сейчас позволяет менять параметры Campaign, активировать/деактивировать её, добавлять/удалять товары и изменять product-level bids. При этом API быстро эволюционирует: в мае 2026 dailyBudget был помечен deprecated, а в июне менялись bid-related параметры. Поэтому Action называется CAMPAIGN_ADJUST_BUDGET, а не именем конкретной API-ручки или поля. GitHub

5. Action Catalog — закрытый
Deep не получает инструкцию:
«Придумай действие».
Backend передаёт:
Action Menu
Например для конкретного SKU:
SKU_ADJUST_PRICE
SKU_INCREASE_REPLENISHMENT
SKU_ADJUST_AD_BID
SKU_JOIN_PROMOTION
...
И AI может выбрать только существующий Action Type.
Если в Catalog нет:
SKU_CHANGE_IMAGES
модель не может предложить это как Action.
Она может упомянуть что-то в Recommendation только если данные это поддерживают, но отдельной Action-card не возникнет.

6. Почему это особенно важно для Funnel / Content
Сейчас у нас нет полноценного Content Quality domain и Evidence.
Поэтому я не включаю в Action Catalog v1:
IMPROVE_PRODUCT_CARD
CHANGE_TITLE
CHANGE_IMAGES
CHANGE_DESCRIPTION
SEO_OPTIMIZATION
Даже если AI знает из общих знаний, что плохая карточка может снижать conversion.
У него нет factual evidence по карточке seller.
Это хороший пример того, как закрытый Action Catalog защищает нас от галлюцинаций.

8. Action Family
Я бы использовал стабильные семейства:
PRICING
INVENTORY
ADVERTISING
PROMOTION
ASSORTMENT
ACCOUNT_HEALTH
Не:
SEARCH
FINANCE
FUNNEL
Почему?
Search, Finance и Funnel в основном являются диагностическими domains.
Они помогают понять, что произошло, но сами по себе не являются управленческими рычагами.
Например Funnel может поддержать:
SKU_ADJUST_PRICE
SKU_ADJUST_AD_BID
но мы не создаём:
SKU_FIX_FUNNEL
потому что это бессмысленное действие.

9. ACCOUNT Actions v1
Здесь я рекомендую быть очень консервативным.
ACCOUNT_RATING_REMEDIATION
Target:
ACCOUNT
Используется, когда Ozon Account Health показывает конкретную provider-defined проблему.
Например:
provider rating:
FBS delays = CRITICAL

provider error events:
SELLER_DELAY
Action:
Снизить количество задержек FBS, влияющих на рейтинг Ozon.
Parameters:

related_rating_keys[]
provider_error_types[]
Все keys должны реально существовать в Account Health Evidence.

10. Почему пока только один Account Action
Я не рекомендую сразу вводить десяток размытых типов:
OPTIMIZE_ACCOUNT
IMPROVE_FINANCE
IMPROVE_BUSINESS
IMPROVE_SUPPLY
Это превратится в мусорный Action Catalog.
Если проблема может быть адресована конкретной:

SKU
Campaign
лучше адресовать её туда.
Account Action нужен там, где сама проблема действительно account-level.

Category Actions — по природе координированные планы, а не прямые Ozon API команды.
Мы уже специально сделали Category полноценным Action Target, поэтому я предлагаю пять типов.
CATEGORY_REPRICING_PLAN
Например:
Пересмотреть ценовую позицию категории «Кофемашины», где снижение сосредоточено среди SKU с недавним повышением цены.
Parameters:
direction:
LOWER
RAISE
MIXED

affected_material_sku_refs[]

CATEGORY_REPLENISHMENT_PLAN
Например:
Увеличить пополнение категории, поскольку несколько значимых SKU имеют низкое покрытие.
Parameters:
direction:
INCREASE
DECREASE
MIXED

affected_material_sku_refs[]

CATEGORY_ADVERTISING_REALLOCATION
Например:
Перераспределить рекламную нагрузку внутри категории.
Parameters:
intent:
INCREASE
DECREASE

related_material_campaign_refs[]
affected_material_sku_refs[]

CATEGORY_PROMOTION_PLAN
intent:
EXPAND_PARTICIPATION
REDUCE_PARTICIPATION
CHANGE_TERMS
MIXED

CATEGORY_ASSORTMENT_RATIONALIZATION
Для ситуации, когда Category-level evidence показывает структурную проблему ассортимента.

MIXED
Но не:
CREATE_NEW_UNKNOWN_SKUS

12. Важное правило Category Actions
Если ситуация полностью сводится к одному SKU:
SKU 417
не надо создавать одновременно:
CATEGORY_REPRICING_PLAN

и

SKU_ADJUST_PRICE
только ради количества Actions.
Category Action нужен, когда Deep действительно видит coordinated category pattern.
Если проблема локальная — SKU Action лучше.
Это semantic правило prompt/evals, а не backend rule.

13. SKU Actions — основной operational catalog
Именно здесь будет большая часть Actions.

14. SKU_ADJUST_PRICE
Target:
SKU
Parameters:
recommended_price: Money
Я предлагаю обязательно требовать конкретную цену.
Если AI способен сказать только:
Возможно, стоит пересмотреть цену,
это Recommendation.
Не Action.
Action появляется, когда он готов сказать:
Рекомендованная цена — 2 190 ₽.

15. Почему не передаём direction
Если:
current_price = 2300
recommended_price = 2190
backend сам знает:
direction = DECREASE
delta = -110
delta_pct = -4.78%
AI не должен одновременно отправлять:
direction = DECREASE
recommended_price = 2190
delta = -110
и создавать три источника возможной арифметической ошибки.

16. Price validation
Backend проверяет:
recommended_price &gt; 0

currency = current currency

recommended_price != current_price
Если известна provider min-price floor:
recommended_price &gt;= min_allowed_price
Если AI рекомендует:
1 500 ₽
при известном:
min_allowed = 1 800 ₽
Action invalid.
Это техническая валидация, не semantic repair.

17. SKU_INCREASE_REPLENISHMENT
Для:
текущий запас мал относительно спроса
+
пополнение отсутствует/недостаточно
Parameters:
recommended_units: integer | null
Число не обязательно.
Например:
Action:
увеличить пополнение SKU
может быть полезным даже если данных недостаточно для честного расчёта конкретного количества.
Если AI считает количество обоснованным:
recommended_units = 180
может его дать.
Но это:
рекомендованное количество,
не:
оптимальное количество.

18. SKU_REDUCE_REPLENISHMENT
Используется только когда существует factual replenishment/inbound context, который реально можно сократить.
Parameters:
recommended_units_reduction: integer | null
Нельзя создать его просто потому, что:
Stock высокий
если никакого будущего replenishment вообще нет.
Тогда нужна другая Recommendation, например Price/Promotion/Monitor.

19. Очень важная будущая execution-граница
SKU_INCREASE_REPLENISHMENT никогда нельзя автоматически переводить в вызов /v2/products/stocks, чтобы просто нарисовать seller больший FBS stock.
Stock API должен отражать реально имеющийся физический запас, а не желаемое количество.
Для FBO replenishment существует отдельный Supply workflow. GitHub
Поэтому semantic Action:
INCREASE_REPLENISHMENT
и provider command:
UPDATE_STOCK
не являются одним и тем же.

Target:
SKU
Related:

Parameters:

Action допустим только если:

Current Performance API имеет отдельные методы для минимальных/конкурентных ставок и product-level bid updates, но эти contracts меняются, поэтому bid action будет capability-gated. GitHub

22. SKU_JOIN_PROMOTION
Related:
PROMOTION
Parameters:

Backend проверяет:

SKU != already participant

Текущий Ozon API действительно разделяет candidates и participating products и предоставляет отдельные write-операции добавления товара в акцию. GitHub

  "target": {
    "kind": "SKU",
    "id": "417"
  },

  "parameters": {
    "recommended_price": {
      "amount": "2190",
      "currency": "RUB"
    }
  },

  "recommendation_ordinal": 2,

  "finding_ordinals": [1],

  "fact_handles": [
    "f_021",
    "ef_007",
    "ef_012"
  ]

38. Никаких system IDs от AI
Модель не придумывает:
action_id
finding_id
recommendation_id
Она использует local ordinals внутри своего structured output:
finding #1
recommendation #2
После validation backend создаёт настоящие IDs.

39. Action Proposal не содержит отдельный title
Например AI не нужно ещё раз писать:
title:
"Снизьте цену!"
У нас уже есть:
Action Type
Recommendation statement
Recommendation rationale
Parameters
Publication Projector позже может детерминированно показать:
Скорректировать цену SKU
и рядом:
2 300 ₽ → 2 190 ₽.
Это уменьшает лишний generated prose.

40. Target-state лучше delta
Для любых числовых Actions я предпочитаю:
recommended_price = 2190
а не:
decrease_price_by = 4.78%
Campaign:
recommended_weekly_budget = 70000
а не:
increase_budget_by = 20%.
Bid:
recommended_bid = 25
а не:
+5.
Почему?
Target state:
однозначен;
легче валидируется;
легче отображается;
безопаснее для будущего executor;
не зависит от того, изменилось ли исходное значение между расчётами.

41. Delta всегда считает backend
Например:
current price:
2300

recommended:
2190
Backend формирует:
absolute_delta = -110
pct_delta = -4.78%
AI не пересчитывает.

42. Numerical recommendations — только там, где schema разрешает
Можно:
SKU_ADJUST_PRICE
→ recommended_price

CAMPAIGN_ADJUST_BUDGET
→ recommended_budget

SKU_ADJUST_AD_BID
→ recommended_bid
Не нужно позволять числовое поле каждому Action на всякий случай.
Например:
ACCOUNT_RATING_REMEDIATION
не имеет:
recommended_rating = 96.4
если seller напрямую этот rating не устанавливает.

43. Не допускаем expected business outcome
Action schema не содержит:
expected_revenue_uplift
expected_orders_growth
expected_roi
expected_profit
success_probability
Потому что у нас нет causal forecasting model.
AI может сформулировать intended outcome в Recommendation:
увеличить доступность товара.
Но не:
это принесёт +320 000 ₽.

44. Required Evidence Policy
Каждый Action Type имеет metadata:
required_domains
required_capabilities
required_fact_classes
allowed_readiness
Например:
SKU_ADJUST_PRICE
минимально требует:
current Price usable
Sales Demand usable
Price factual context

SKU_INCREASE_REPLENISHMENT
current Stock usable
Sales Demand usable
Supply context:
required if applicable/available

SKU_ADJUST_AD_BID
Advertising READY/PARTIAL allowed by policy
Campaign↔SKU relation known
bid semantics known

SKU_JOIN_PROMOTION
Promotion capability usable
candidate eligibility known

45. Но backend не проверяет «правильность бизнес-решения»
Это принципиально.
Он не пишет:
if coverageDays &lt; 3 {
    allow replenishment
}
или:
if drr &gt; 30 {
    allow bid decrease
}
Это опять был бы semantic rule engine.
Backend проверяет:
есть ли данные, необходимые для такого решения?
AI решает:
оправдано ли само решение?

46. Action Menu формируется run-specific
Глобально у нас:
19 types.
Но конкретному seller/run Deep может увидеть только:
12.
Например:
Promotions unavailable → promo actions исключены;
Advertising unavailable → ad actions исключены;
Campaign strategy unknown → strategy action исключён;
SKU archived → desired_state=ARCHIVED недоступен как no-op;
Promotion participant → JOIN недоступен, но LEAVE доступен.
То есть Deep получает только фактически применимые действия.

105. Архитектурный контракт Action Taxonomy / Contract
Предлагаю зафиксировать:
Action Aivion является закрытым, versioned и fact-grounded управленческим предложением, создаваемым исключительно Deep Analysis из Recommendation со статусом ACTIONABLE_NOW. V1 Actions являются read-only recommendations и никогда непосредственно не вызывают provider write API. Action Proposal не является executable command; будущая execution architecture обязана отдельно подтвердить пользователя, перечитать current state и повторно проверить provider constraints.
Action Target v1 ограничен Account, seller-bearing leaf Category, SKU и Campaign. Target должен быть Materiality-selected main entity и присутствовать в Discovery Pack. Entity, раскрытая только Evidence, может участвовать в Findings, но не может стать Action Target. Если Action параметр фактически изменяет другую main Action Entity, эта entity также должна пройти Materiality; supporting entities Promotion/Supply/Search Query/Warehouse могут использоваться только как factual/context refs.
Deep получает run-specific Action Menu, построенное backend из versioned Action Catalog, Target type, Capabilities и factual state. AI не может изобретать Action Types или произвольные parameters. Каждый Action Type имеет stable business-semantic key, target kind, action family, typed parameter schema, applicability/capability requirements, conflict group и optional future execution metadata. Ozon endpoint names не являются Action identities.
V1 Catalog intentionally small: Account Health remediation; coordinated Category pricing/replenishment/advertising/promotion/assortment plans; concrete SKU price/replenishment/advertising/promotion/catalog-state actions; Campaign budget/state/strategy/product-set actions. Content/SEO, warehouse/cluster, arbitrary Finance/Funnel/Search actions отсутствуют до появления соответствующей canonical factual architecture.
Числовые Actions используют recommended target state, а не дублируют current/delta calculations. Current values и deltas принадлежат backend. Known provider bounds, currency, state transitions, membership/eligibility и no-op conditions валидируются технически. Backend не решает, является ли бизнес-рекомендация хорошей, не меняет recommended values и не semantic-repair'ит output.
Каждый Action имеет обязательную chain Action → Recommendation → Finding → Fact Handles → Factual API provenance. Action не хранит unsupported quantitative expected effect, revenue uplift, ROI или self-reported confidence. Actions globally ordered Deep Analysis, но отдельные HIGH/MEDIUM/LOW severity/priority scores v1 не вводятся.
Action Type и Provider Execution Mapping являются разными versioned layers. Текущие Ozon write capabilities подтверждают наличие будущих execution paths для Price, Campaign, Promotion и Supply операций, однако API contracts быстро меняются; semantic Action остаётся стабильным, execution adapter эволюционирует независимо.

Один продуктовый вопрос я бы сейчас действительно закрыл
Он уже относится не к AI reasoning, а к тому, как Actions будут жить между ежедневными публикациями.
Пример:
20 августа Aivion создаёт:
SKU 417
SKU_INCREASE_REPLENISHMENT
21 августа новый анализ снова приходит к:
SKU 417
SKU_INCREASE_REPLENISHMENT
Я не рекомендую показывать пользователю две разные одинаковые карточки:
20.08 Пополнить SKU 417
21.08 Пополнить SKU 417
Я предлагаю будущую модель:
Action Case
SKU417 + INCREASE_REPLENISHMENT
        │
        ├─ Proposal 20.08
        ├─ Proposal 21.08
        └─ Proposal 22.08
Пользователь видит одно открытое действие, а новые Publications обновляют его factual basis и последнюю рекомендацию.
Если пользователь отметил его:
DONE
а через некоторое время ситуация снова возникла, тогда создаётся новый occurrence, а не оживляется старая выполненная задача.
То же для:
DISMISSED
— старую карточку не переписываем задним числом; новая действительно возникшая ситуация может позднее породить новый occurrence.
Я рекомендую именно такую persistent Action Case модель вместо независимого списка Actions каждой ежедневной Publication. Если согласен — зафиксируем это вместе с Action Contract, и следующим этапом можно проектировать Publication Model + Projection, где как раз свяжем Deep Result, Actions и будущие Dashboard blocks.
Я согласился с рекомендацией
Да, этот момент требует отдельного дополнения к ТЗ. После более критического разбора я бы немного уточнил предыдущую модель: объединение нескольких SKU должно существовать, но не на уровне канонического Action. Канонический Action остаётся атомарным, а общий смысл объединяется на уровне multi-entity Recommendation, после чего Publication формирует из связанных Actions Action Group для пользователя.
Это принципиально важное различие.
Дополнение к ТЗ: Multi-entity Recommendations и группировка Actions
Цель доработки
Обеспечить корректную обработку ситуаций, когда Deep Analysis формирует одно общее управленческое решение, применимое сразу к нескольким однотипным сущностям, например:
пополнить 4 SKU с отсутствующим остатком;
снизить цены у 3 SKU;
увеличить рекламные ставки у 5 SKU одной кампании;
исключить несколько SKU из одной акции;
архивировать группу неактуальных SKU.
При этом необходимо сохранить:
независимое factual grounding каждого SKU;
отдельные рекомендуемые параметры;
отдельный жизненный цикл каждого действия;
корректную дедупликацию Actions между публикациями;
возможность частичного выполнения;
возможность будущего batch execution через Ozon API;
удобное отображение пользователю без десятков однотипных карточек.

1. Основной архитектурный принцип
Необходимо различать три уровня:
Recommendation
    ↓
Atomic Actions
    ↓
Action Group / UI Projection
Например Deep Analysis определил:
SKU 417 → остаток 0 → пополнить 120 шт.
SKU 522 → остаток 0 → пополнить 40 шт.
SKU 816 → остаток 0 → пополнить 250 шт.
SKU 901 → остаток 0 → пополнить, qty определить нельзя
Смысловая рекомендация одна:
Пополнить четыре значимых SKU с отсутствующим sellable stock и сохраняющимся спросом.
Но канонически создаются четыре Actions:
SKU_INCREASE_REPLENISHMENT → SKU 417
SKU_INCREASE_REPLENISHMENT → SKU 522
SKU_INCREASE_REPLENISHMENT → SKU 816
SKU_INCREASE_REPLENISHMENT → SKU 901
А пользователю они могут отображаться одной карточкой:
Пополнить 4 товара без остатков
с раскрывающимся списком конкретных SKU.

2. Один Action по-прежнему имеет ровно один основной target
Уже утверждённое правило необходимо сохранить:
Action.target = exactly 1 Action Target
Допустимые target:
ACCOUNT
LEAF_CATEGORY
SKU
CAMPAIGN
Поэтому запрещён контракт вида:
{
  "action_type": "SKU_INCREASE_REPLENISHMENT",
  "targets": [
    "SKU417",
    "SKU522",
    "SKU816",
    "SKU901"
  ]
}
Для обычного SKU Action.
Почему это важно: у каждого SKU собственные данные, Recommendation parameters, Action Case и eventual execution result.

3. Почему нельзя хранить «пополнить 4 SKU» одним Action
Сегодня:
SKU 417 → нужно +120
SKU 522 → нужно +40
SKU 816 → нужно +250
SKU 901 → quantity неизвестно
Завтра:
SKU 417 → уже пополнен
SKU 522 → всё ещё требует пополнения
SKU 816 → всё ещё требует пополнения
SKU 901 → пользователь отклонил рекомендацию
Если всё было одним Action, возникает неразрешимая неоднозначность:
Action выполнен или нет?
Для четырёх атомарных Actions ответ очевиден.

4. Изменение Deep Analysis Recommendation Contract
Вот здесь предыдущий контракт нужно расширить.
Ранее Recommendation фактически подразумевала один target_entity.
Этого недостаточно.
Recommendation должна поддерживать:
scope_type:
SINGLE_ENTITY
ENTITY_SET
При SINGLE_ENTITY:
subject_entities = [SKU417]
При ENTITY_SET:
subject_entities = [
    SKU417,
    SKU522,
    SKU816,
    SKU901
]

5. Ограничение ENTITY_SET v1
Я рекомендую в v1 разрешить только однородный набор сущностей.
Например:
4 × SKU
или:
3 × Campaign
но не:
SKU417
Campaign58
Category12
в одной multi-entity Recommendation.
Если бизнес-ситуация связывает несколько типов сущностей, Deep может создать несколько Findings/Recommendations, связанных общим reasoning.
Это существенно упрощает контракт.

6. Все участники ENTITY_SET должны пройти Materiality
Наше последнее правило полностью сохраняется.
Например Deep хочет сформировать:
Пополнить SKU 417, 522, 816 и 999.
Backend проверяет:
417 → Material Entity ✅
522 → Material Entity ✅
816 → Material Entity ✅
999 → появился только Evidence ❌
Такой набор недопустим.
SKU 999 можно использовать в Finding как related evidence, но нельзя включать в управленческую Recommendation/Action.

7. Multi-entity Recommendation не является Action
Например:
Recommendation R7

scope = ENTITY_SET

subjects:
SKU417
SKU522
SKU816
SKU901

statement:
«Пополнить товары с отсутствующим запасом
и сохраняющимся спросом»

actionability:
ACTIONABLE_NOW
Из неё могут появиться:
A1 → SKU417
A2 → SKU522
A3 → SKU816
A4 → SKU901
Все четыре ссылаются:
recommendation_ref = R7
Но каждый имеет собственные:
finding_refs
fact_handles
parameters
target

8. Grounding остаётся индивидуальным
Общий Recommendation не означает, что можно перестать доказывать необходимость каждого SKU.
Например:
Action A1:
SKU417
recommended_units = 120

facts:
stock=0
recent demand=...
coverage=0
Action A2:
SKU522
recommended_units = 40

facts:
stock=0
recent demand=...
coverage=0
И так далее.
Общая формулировка:
Пополнить товары без остатков
не заменяет individual factual basis.

9. Один Recommendation может ссылаться на несколько Findings
Например:
Finding F1 → SKU417
Finding F2 → SKU522
Finding F3 → SKU816
Finding F4 → SKU901
Recommendation:
R7
→ F1
→ F2
→ F3
→ F4
А каждый Action дополнительно указывает те Findings, которые относятся именно к его target.

10. Action Group не должен становиться новым Action Target
Это особенно важно.
Не вводим:
Action Target = SKU_GROUP
или:
Action Target = PRODUCT_SET
У нас по-прежнему только четыре разрешённых target.
Action Group — контейнер/проекция над уже существующими Actions.

11. Где формируется Action Group
Я предлагаю не заставлять AI возвращать отдельный ActionGroup object.
Deep уже сказал всё необходимое:
Recommendation R7
    ↓
A1
A2
A3
A4
Publication Projector детерминированно видит:
один Recommendation
+
одинаковый Action Type
+
несколько targets
и создаёт:
Action Group
Таким образом backend ничего семантически не придумывает.

12. Условия автоматической группировки
Actions объединяются в одну группу только при одновременном выполнении следующих условий:
same Recommendation
+
same Action Type
+
same target kind
+
compatible action context
+
member count &gt;= 2
Это очень важное правило.

13. Почему недостаточно просто одинакового Action Type
Допустим есть:
SKU417 → снизить цену
потому что Price выросла перед снижением Sales.
И:
SKU999 → снизить цену
потому что товар участвует в другой ценовой механике и текущая цена выбивается из недавнего контекста.
Это две разные Recommendations.
Даже если обе имеют:
SKU_ADJUST_PRICE
их не надо автоматически объединять в:
Снизить цены 2 товаров.
Иначе пользователь потеряет смысл, почему каждое действие появилось.
Поэтому главный grouping anchor:
shared recommendation_ref

14. Нельзя делать semantic grouping в backend
Backend не должен пытаться определить:
Эти четыре рекомендации похожи по тексту на 89%, объединим.
Никаких embeddings, similarity или rules по словам.
Deep сам формирует общую Recommendation, если действительно считает Actions частью одного управленческого решения.
Backend лишь реализует эту структуру.

15. Совместимый Action Context
Некоторые Actions требуют дополнительного context.
Например:
SKU_ADJUST_AD_BID
должен иметь:
campaign_ref
Поэтому:
SKU417 → Campaign58
SKU522 → Campaign58
можно сгруппировать.
Но:
SKU417 → Campaign58
SKU522 → Campaign79
в одной Action Group я бы не объединял.
Несмотря на одинаковый Action Type.

16. Promotion Actions
Для:
SKU_JOIN_PROMOTION
одна группа должна относиться к одной Promotion.
Можно:
Добавить 5 товаров в акцию «Распродажа августа».
Нельзя:
Добавить 5 товаров в акции
если фактически:
3 → Promotion91
2 → Promotion105
Это две группы.

17. Catalog state
Для:
SKU_CHANGE_CATALOG_STATE
одинаковым должен быть desired_state.
Можно:
Архивировать 5 товаров.
Но нельзя одной группой:
3 → ARCHIVED
2 → ACTIVE

18. Price Actions
Для Price группировать можно даже при разных recommended prices.
Например:
SKU417:
2300 → 2190

SKU522:
1490 → 1390

SKU816:
5900 → 5490
UI:
Скорректировать цены 3 товаров
А внутри пользователь видит индивидуальное значение для каждого.

19. Replenishment
Аналогично:
Пополнить 4 товара
может содержать:
SKU417 → 120 шт.
SKU522 → 40 шт.
SKU816 → 250 шт.
SKU901 → quantity не определено
Группа не требует одинаковых parameters.
Она требует одинакового управленческого намерения.

20. Не группируем разные Action Types
Даже если Recommendation одна.
Например Deep сформировал Recommendation:
Усилить поддержку быстрорастущих товаров.
И создал:
SKU417 → INCREASE_REPLENISHMENT
SKU522 → INCREASE_REPLENISHMENT

SKU417 → ADJUST_AD_BID
SKU522 → ADJUST_AD_BID
Это не одна гигантская карточка.
Publication формирует:
Group 1:
Пополнить 2 товара

Group 2:
Изменить рекламные ставки 2 товаров
Обе могут ссылаться на один Recommendation.
Так гораздо понятнее.

21. Не вводим вложенные группы
V1:
Action Group
    ↓
Atomic Actions
и всё.
Никаких:
Category Group
  ↓
Replenishment Group
    ↓
Subgroup by warehouse
      ↓
Actions
Это быстро сделает Actions UI неуправляемым.

22. Разница между Action Group и Category Action
Это один из самых важных моментов.
Grouped SKU Actions
Пополнить SKU417, SKU522, SKU816, SKU901.
Смысл:
выполнить однотипное действие отдельно над четырьмя конкретными SKU.
Поэтому:
4 × SKU Actions

Category Action
Пересмотреть стратегию пополнения категории «Кофемашины».
Это уже решение уровня:
Category
и поэтому:
1 × CATEGORY_REPLENISHMENT_PLAN

23. Как выбирать между ними
Если Recommendation можно полностью разложить:
что сделать с SKU417
что сделать с SKU522
что сделать с SKU816
и каждый пункт имеет самостоятельное выполнение — это SKU Actions + Group.
Если смысл рекомендации:
изменить управленческий подход к категории в целом,
то это Category Action.

24. Не надо создавать оба уровня без необходимости
Плохой output:
CATEGORY_REPLENISHMENT_PLAN
Category X

+

SKU_INCREASE_REPLENISHMENT 417
SKU_INCREASE_REPLENISHMENT 522
SKU_INCREASE_REPLENISHMENT 816
если Category Action просто повторяет три SKU Actions.
Deep prompt должен избегать такой redundancy.
Category Action нужен, когда в нём действительно есть дополнительный category-level смысл.
Это semantic quality rule, который проверяем evals, а не backend.

25. Campaign Action — отдельный случай
Например:
CAMPAIGN_ADJUST_PRODUCT_SET
имеет:
target = Campaign58

remove_skus:
417
522
816
Это один Action, несмотря на три SKU.
Почему?
Потому что непосредственно изменяемый бизнес-объект — Campaign.
Управленческая операция:
изменить product set Campaign58.
SKU здесь являются параметрами Campaign Action.

26. При этом child Materiality rule сохраняется
Если Campaign Action меняет SKU:
417
522
816
все они должны быть Material Entities.
Иначе Campaign Action превращается в обход Materiality.

27. Persistent Action Case остаётся атомарным
Это ещё одна фундаментальная часть.
Для примера:
Action Case C1:
SKU417 + INCREASE_REPLENISHMENT

C2:
SKU522 + INCREASE_REPLENISHMENT

C3:
SKU816 + INCREASE_REPLENISHMENT

C4:
SKU901 + INCREASE_REPLENISHMENT
Не создаём один:
Action Case:
SKUs [417,522,816,901]

28. Action Group не имеет собственного независимого lifecycle
Это изменение относительно самого первого упрощённого объяснения, и я считаю его правильным.
Canonical statuses существуют у child Action Cases.
Например:
SKU417 → DONE
SKU522 → OPEN
SKU816 → OPEN
SKU901 → DISMISSED
Группа лишь отображает:
2 из 4 требуют действия.
Не существует отдельной истины:
group.status = ?
которая могла бы конфликтовать с дочерними Actions.

29. Статус группы вычисляется
Для UI можно показать:
4 actions

2 open
1 done
1 dismissed
Но это derived projection.
Не отдельный mutable business state.

30. Состав группы может меняться между Publications
Это очень важный кейс.
20 августа:
Group:
417
522
816
901
21 августа:
417 → уже не требует Action
522 → требует
816 → требует
901 → требует
Текущая проекция:
Пополнить 3 товара.
При этом историческая Publication 20 августа остаётся неизменной и продолжает показывать четыре.

31. Поэтому Action Group не надо делать долгоживущей canonical сущностью
Это важный результат анализа.
Долгоживущая сущность:
Action Case
Группа:
Publication/UI Projection
Потому что её membership естественным образом зависит от текущей Publication.

32. Нужна корректировка идентичности Action Case
Многосущностный сценарий выявляет ещё одну важную деталь.
Недостаточно идентифицировать Case только:
target + action_type
Например:
SKU417 + SKU_ADJUST_AD_BID
может относиться к:
Campaign58
или:
Campaign79.
Это совершенно разные Actions.
Поэтому canonical Action Case identity должна быть:
seller
+
action_type
+
target
+
normalized_action_context
+
intent_signature

33. Что такое normalized_action_context
Например:
SKU_ADJUST_AD_BID:
campaign=58
SKU_JOIN_PROMOTION:
promotion=91
Для обычной Price Action:
context = none

34. Что такое intent_signature
Нужно также различать противоположные рекомендации.
Например сегодня:
SKU_ADJUST_PRICE:
2300 → 2190
а через неделю:
SKU_ADJUST_PRICE:
2100 → 2400
Это уже не продолжение старого Action Case в нормальном продуктовом смысле.
Поэтому backend может детерминированно вычислять:
PRICE:
INCREASE / DECREASE

BUDGET:
INCREASE / DECREASE

BID:
INCREASE / DECREASE

CAMPAIGN_STATE:
ACTIVE / PAUSED

CATALOG_STATE:
ACTIVE / ARCHIVED

35. Зачем это нужно
Если recommendation остаётся:
price decrease
но число меняется:
2190 → 2150
это тот же Action Case с обновлённым proposal.
Если направление полностью поменялось:
DECREASE
→
INCREASE
старый Case не должен незаметно превратиться в противоположное действие.
Это уже новый occurrence.

36. Для такого случая нужен system state SUPERSEDED
Я рекомендую предусмотреть его при проектировании полного Action Case lifecycle.
Например:
old Action Case:
Decrease price
→ SUPERSEDED

new Action Case:
Increase price
→ OPEN
Это лучше, чем переписывать историю старого Action.
Сам полный lifecycle логичнее окончательно закрыть на Publication/Actions persistence этапе.

37. Как Deep должен возвращать multi-entity Recommendation
Упрощённо:
{
  "scope_type": "ENTITY_SET",
  "subject_entities": [
    "SKU417",
    "SKU522",
    "SKU816",
    "SKU901"
  ],
  "statement": "Пополнить товары с отсутствующим запасом и сохраняющимся спросом.",
  "actionability": "ACTIONABLE_NOW",
  "finding_refs": [1, 2, 3, 4]
}
Далее:
Action 1 → SKU417 → Recommendation R7
Action 2 → SKU522 → Recommendation R7
Action 3 → SKU816 → Recommendation R7
Action 4 → SKU901 → Recommendation R7

38. Publication Projector создаёт group
Алгоритм полностью детерминированный:
Validated Actions
        ↓
partition by:
recommendation_ref
action_type
target_kind
normalized context
        ↓
if count &gt;= 2
→ Action Group Projection
Никакого AI здесь больше нет.

39. Group title не нужно повторно генерировать AI
Например Action Type:
SKU_INCREASE_REPLENISHMENT
может иметь presentation template:
1 → «Пополнить товар»
N → «Пополнить N товаров»

40. А business explanation берём из Recommendation
Например:
У товаров отсутствует sellable stock при сохраняющемся спросе.
Это уже написал Deep.
Так мы избегаем нового AI-generation на Projection stage.

41. Дополнительный factual qualifier
Если действительно для всех members:
sellable_stock = 0
Projector может детерминированно показать:
Пополнить 4 товара без остатков.
Но только если этот qualifier доказан facts всех участников.
Если:
SKU417 → 0
SKU522 → 0
SKU816 → 3 days
SKU901 → 1 day
название:
Пополнить 4 товара
а не:
4 товара без остатков.
Backend не должен обобщать факт, который не относится ко всей группе.

42. Внутри группы пользователь видит individual facts
Например:

43. Пользователь должен иметь возможность работать с одним child Action
Например:
Пополнить 4 товара
Пользователь раскрывает карточку и может:
SKU417 → DONE
не затрагивая остальные.
Это обязательно.

44. Массовая пользовательская операция
Я также рекомендую предусмотреть:
«Отметить все выполненными»
«Отклонить все»
как bulk UI operation.
Но технически это не изменение Group.
Backend выполняет N отдельных переходов Action Case, связанных одним:
bulk_operation_id
Так сохраняется аудит.

45. Будущая автоматизация Ozon
Здесь атомарная модель особенно важна.
Текущий Ozon интерфейс уже поддерживает массовое добавление/удаление товаров в рекламных кампаниях, а текущий Performance API содержит batch product operations; для некоторых массовых методов документирован лимит до 1000 товаров за запрос. Документы Ozon
При этом Performance contracts изменяются: Ozon обновлял product/bid methods и их параметры в 2026 году. GitHub
Поэтому нельзя делать:
Action Group
=
Ozon API request.

46. Правильная будущая execution model
Например пользователь нажимает:
Применить ко всем 40 SKU.
Execution Layer:
40 Atomic Actions
↓
fresh revalidation каждого
↓
37 valid
3 stale/invalid
↓
compatible Actions объединяются
в provider batches
↓
batch requests к Ozon
↓
результат снова раскладывается
по 37 individual Actions
То есть batch — оптимизация транспорта.
Не business identity.

47. Почему это важно при partial failure
Представим Ozon запрос на несколько SKU.
Результат:
SKU417 → SUCCESS
SKU522 → SUCCESS
SKU816 → ERROR
SKU901 → SUCCESS
Если Aivion хранит один массовый Action:
Что является результатом — SUCCESS или FAILED?
При атомарной модели:
417 DONE
522 DONE
816 FAILED
901 DONE
никакой проблемы нет.

48. Provider batch limits не должны попадать в Action Contract
Сегодня Ozon может разрешать:
500
1000
товаров в конкретной операции. Например текущая Performance documentation отражает batch product operations и отдельные ограничения; в описании product campaigns также существует массовое добавление товаров. GitHub
Завтра лимит может измениться.
Поэтому:
Action Group = 3 000 SKU
архитектурно допустима как recommendation/UI set.

Итоговая формулировка для архитектурного ТЗ
Aivion должен поддерживать multi-entity Recommendations для случаев, когда единое управленческое решение относится к нескольким Material Entities одного типа. Multi-entity Recommendation не является массовым Action и не создаёт новый Action Target. Каждый actionable subject такой Recommendation должен порождать отдельный атомарный Action Proposal с единственным primary target, собственными parameters, Findings, Fact Handles и последующим Action Case.
Однотипные атомарные Actions, сформированные из одной Recommendation и имеющие совместимый action context, могут объединяться Publication Projector в Action Group для пользовательского представления. Action Group является immutable publication/presentation projection и не имеет собственного независимого lifecycle или mutable status. Источником истины остаются отдельные Action Cases.
Группировка не выполняется на основании текстового или semantic similarity. Она определяется детерминированно через общий recommendation_ref, action_type, target_kind и normalized action context. Actions разных типов, относящиеся к разным Recommendations либо имеющие несовместимый Campaign/Promotion context, не объединяются.
Все main entities multi-entity Recommendation и child main entities Actions должны пройти Materiality и присутствовать в Discovery Pack. Evidence-only entities не могут быть добавлены в Action Group как управляемые объекты.
Category/Campaign Actions не заменяются группами SKU Actions, если само управленческое решение относится к Category/Campaign как к единому target. В то же время Category Action не должен дублировать набор SKU Actions без отдельного category-level смысла.
Persistent Action Case остаётся атомарным. Его identity строится на seller + action_type + target + normalized context + intent signature. Повторное предложение того же действия в последующих Publications обновляет factual basis существующего Case; изменение противоположного intent должно рассматриваться как новый occurrence, а предыдущий Case не переписывается.
Будущая возможность массового выполнения не изменяет canonical Action model. Execution Layer может объединять несколько atomic Actions в provider batch только после индивидуальной fresh-state revalidation. Provider batch limits и endpoint contracts принадлежат versioned Execution Mapping и не являются частью Action identity. Частичный provider result всегда разворачивается до отдельных результатов child Actions.
Что я бы сейчас считал правильным решением
Для твоего примера:
«Пополнить товары без остатков — 4 SKU»
идеальная структура именно такая:
1 multi-entity Recommendation
        ↓
4 atomic SKU Actions
        ↓
4 persistent Action Cases
        ↓
1 Action Group в интерфейсе
Это одновременно решает удобство интерфейса, корректность AI, аудит, ежедневное обновление Actions и будущую автоматизацию через Ozon.
Единственный небольшой продуктовый момент, который я бы ещё зафиксировал позднее при проектировании раздела «Действия»: разрешаем ли пользователю на групповой карточке нажимать «Выполнено для всех» / «Отклонить все». Архитектурно я рекомендую разрешить, но реализовывать это как bulk-команду над individual Action Cases, а не как изменение статуса самой группы.
