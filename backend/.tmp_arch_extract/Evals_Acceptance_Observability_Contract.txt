Правильно ли Aivion считает факты?Качественно ли AI понимает эти факты и предлагает действия?Работает ли вся система стабильно в production и не деградировала ли после очередной доработки?
Современная практика evals как раз рекомендует оценивать не модель в вакууме, а весь конкретный workflow — с тем же контекстом, tools, budgets, retry policy и harness, которые используются продуктом. Для бизнес-сценариев OpenAI рекомендует использовать реальные кейсы и редкие, но дорогие ошибки, а LLM-graders регулярно сверять с экспертной оценкой. OpenAI
Aivion Evals / Acceptance / Observability Contract
1. Главный принцип
У Aivion не должно существовать одного абстрактного AI Quality Score.
Мы разделяем качество на четыре независимых контура:
Контур
Что проверяет
Factual Correctness
правильно ли собраны и рассчитаны данные
AI Semantic Quality
правильно ли AI понял ситуацию
Product Consistency
согласованы ли Dashboard / Actions / Chat / Publication
Operational Reliability
стабильно ли всё запускается, восстанавливается и работает
Это принципиально.
Например AI может написать очень разумный текст, но использовать неправильную сумму заказов.
Результат всё равно:
FAIL
И наоборот: все цифры могут быть идеально правильными, но AI может не заметить главный риск seller.
Тогда factual layer:
PASS
а AI quality:
FAIL.

2. Что может блокировать Publication
Очень важное разделение.
В production pipeline Publication блокируют только детерминированные проверки, которые можно однозначно вычислить программно.
Например:
FactRef не существует                   → BLOCK

Action target недопустим               → BLOCK

SKU относится другому seller           → BLOCK

previous Action не revalidated          → BLOCK

Deep schema invalid                     → BLOCK

Action параметр нарушает schema         → BLOCK

projection содержит другую Publication  → BLOCK
Но не:
LLM judge считает insight недостаточно хорошим
→ BLOCK
Никакого третьего AI-вызова:
Discovery AI
Deep AI
Judge AI
в production generation не появляется.
Сохраняем утверждённые:
Discovery
↓
Evidence
↓
Deep
LLM-graders работают offline, используя уже сохранённые immutable artifacts.
OpenAI Evals сейчас поддерживает deterministic graders, model graders и комбинированные graders; это хорошо подходит для offline harness, но человеческая экспертиза всё равно необходима для проверки самого grader. 3. Четыре уровня проверки
Итоговая система:
LEVEL 1
Deterministic Runtime Validation
        ↓
может блокировать Publication

LEVEL 2
Offline Regression Evals
        ↓
может блокировать новую версию кода/model/prompt

LEVEL 3
Production Quality Sampling
        ↓
выявляет деградацию на реальных данных

LEVEL 4
Human Expert Review
        ↓
калибрует rubrics/graders и оценивает сложные случаи
Это разные механизмы.

4. Eval не должен запускаться на живом Ozon
Любой regression test воспроизводится на замороженном:
Factual Universe
+
contract versions
+
Landscape
+
AI Pack
+

То есть:
Eval
↓
immutable test fixture
а не:
Eval
↓
сходили сегодня в Ozon
↓
получили уже другие данные
Иначе результат нельзя воспроизвести.

8. Dataset обязательно делим на Development и Holdout
Нельзя бесконечно править prompt именно под все известные eval cases.
Иначе мы получим:
eval 99%
но только потому, что prompt фактически натренировали на тест.
Поэтому:
DEV
→ видим результаты
→ используем для итераций

HOLDOUT
→ не используем при ежедневном prompt tuning
→ запускаем как release gate
Отдельно добавляем свежие real-world production cases.
OpenAI отдельно указывает contamination и возможность «подогнать» систему под eval harness как угрозы валидности оценки. OpenAI

16. Materiality важнее recall, чем precision
Если Materiality взял лишние 5 SKU:
немного увеличили pack.
Если Materiality не взял главный SKU, Discovery уже физически не сможет его обнаружить.
Поэтому оптимизируем:
Recall &gt; Precision.

17. Materiality metrics
Основные:
Critical Entity Recall
General Material Entity Recall

Selection Size
Selection Diversity

Lane Coverage

Anchor Coverage

18. Я предлагаю такой initial acceptance target
Для expert-labelled MUST_INCLUDE:
Critical recall = 100%
То есть ни один критичный entity в golden suite нельзя потерять.
Для остальных material entities первоначальный target:
≥95% recall
Это versioned eval threshold, а не навечно зашитая формула.
После реальных данных сможем откалибровать.

19. Проверяем diversity
Materiality не должен вернуть условно:
50 SKU
из одной категории только потому, что там большой оборот, пропустив существенные кампании и другие категории.
Тестируются:
lane diversity
domain exposure
category concentration
campaign presence
при наличии соответствующих фактов.

20. Проверяем symmetry
В dataset обязательно должны быть:
сильное ухудшение;

сильное улучшение.
Positive changes также должны попадать в Materiality.
Иначе AI будет системно видеть только проблемы.

Не раздробил ли один вопрос на пять одинаковых Threads?

30. Groundedness — hard deterministic
Если Finding говорит:
продажи снизились на 18%
то должен существовать FactRef, подтверждающий именно этот показатель.
Для numeric/domain assertions:
100% grounded
Иначе Publication блокируется validator.

31. Semantic Grounding
Сложнее:
основной причиной является stock.
Backend не способен однозначно доказать семантический вывод.
Это уже offline rubric.
Grader должен проверять:
достаточно ли evidence;
не перепутана ли корреляция и причинность;
соблюдён ли causal restraint.

58. Не оцениваем AI-текст через BLEU
Для свободного аналитического ответа бессмысленно требовать:
текст совпадает с эталоном на 82%.
Два совершенно разных текста могут быть одинаково хорошими.
Exact/string match используем для:
enum;
IDs;
numbers;
structured fields.
Semantic text:
rubric grader + human review.

59. LLM Grader architecture
Для сложных outputs используем отдельный:
Eval Grader Policy
Он не обязан совпадать с production model.
Лучше не делать:
GPT-X генерирует
GPT-X говорит, что GPT-X отлично сработал.
Grader получает:
case facts

expected rubric

actual output

allowed limitations
и выставляет не один score, а отдельные dimensions.

131. Нормативное резюме контракта
Я бы зафиксировал его следующим образом:
Aivion использует многоуровневую систему оценки качества, разделяющую factual correctness, AI semantic quality, product consistency и operational reliability. Единого AI quality score не существует.
Production Publication может блокироваться только детерминированными runtime invariants. LLM-graders и human evaluation не входят в критический production path и выполняются offline на immutable factual universes и artifacts.
Все hard factual, isolation, grounding-reference, Publication consistency, Action target и Action continuity invariants требуют 100% выполнения и не имеют error budget.
Materiality оценивается преимущественно по recall; потеря expert-labelled critical entity является release failure. Discovery оценивается по recall важных Threads, отсутствию unsupported/duplicate Threads и корректности Evidence requests.
Deep Analysis оценивается раздельно по Findings, Recommendations и Actions. Numeric/factual grounding проверяется детерминированно; relevance, causal restraint, usefulness и reasonableness оцениваются rubric-based graders и human review.
Все previous current Publication Actions должны иметь revalidation assessment в следующей generation; continuity coverage обязана составлять 100%. Longitudinal eval suite покрывает FULLY_SUPPORTED, PARTIALLY_SUPPORTED, NOT_SUPPORTED, UNVERIFIABLE и SUPERSEDED, а также DONE/DISMISSED recurrence semantics.
Dashboard, Actions и Chat проходят end-to-end consistency evals на одной Publication. Visual regression и responsive tests являются частью frontend acceptance.
Chat оценивается не только по final answer, но также по conversation context, entity resolution, factual tools, grounding, Publication transitions, attachment+cabinet analysis и tool trajectory.
Любая новая model/prompt/schema/policy version сравнивается с accepted baseline на versioned DEV/HOLDOUT/real replay datasets. Крупные AI изменения требуют human review.
Production observability строится на metrics, traces и structured logs. Full prompt/output artifacts не используются как high-cardinality telemetry; для них сохраняются controlled immutable artifacts и hashes/refs.
Human-alerting используется только для urgent, actionable engineering failures. Необычные бизнес-показатели продавца не являются engineering incidents.
Evaluation Run никогда не может Publish и не изменяет production Actions. Production и evaluation orchestration используют одинаковую фактическую архитектуру, но имеют жёстко разделённые side effects.
