
Я повторно прошёл актуальный Aivion-main (7). Сейчас последний migration — 000060; production runtime всё ещё собирается вокруг старых products / orders / sales / daily_*, отдельных sync-пакетов, aipipeline, большого legacy actions, dashboardhome, unifiedanalysis и собственного SQL-аналитического слоя Chat. Поэтому план ниже — не «дорастить существующий Unified Analysis», а построить новый owner-runtime и затем полностью удалить старую бизнес-архитектуру.

Asynq гарантирует at-least-once execution, retries и recovery worker-crash, поэтому сами handlers обязаны быть идемпотентными; Redis нельзя считать состоянием pipeline. GitHub

79. Не полагаемся на Unique() как correctness mechanism
Можно использовать:
TaskID
Unique
для уменьшения мусора в queue.
Но correctness всё равно:
PostgreSQL stage state + lease.
Asynq Unique привязан к TTL/task payload/queue и заканчивается после successful processing или TTL, поэтому это полезная дедупликация, но не durable business lock. GitHub

80. Stage lease
Claim выполняется атомарным SQL:
UPDATE stage
SET
 status=RUNNING,
 lease_owner=?,
 lease_expires_at=?
WHERE
 id=?
 AND
 (
   status=READY
   OR lease_expires_at &lt; now()
 )
RETURNING *
Worker heartbeat продлевает lease.
Если process умер:
другой worker сможет забрать stage.

81. Advisory lock
Не держим PostgreSQL lock весь AI-call.
Но для коротких операций:
create production run

publication pointer switch
можно использовать transaction-level advisory lock seller.
PostgreSQL transaction advisory locks автоматически освобождаются в конце transaction и как раз подходят для короткой application-defined синхронизации. PostgreSQL

212. PostgreSQL failure
Stage ничего не считает completed до DB commit.

Не публикуем state, которого DB не знает.

231. Важные архитектурные решения, которые этот Plan окончательно закрепляет
Первое: новую UCDM не строим через миграцию старых daily_* данных. Источник — Ozon.
Второе: существующие Ozon HTTP-клиенты переиспользуем, существующие business sync-models — нет.
Третье: Factual API становится обязательной границей между canonical DB и AI/Chat.
Четвёртое: PostgreSQL является единственным durable state pipeline; Asynq лишь at-least-once executor. GitHub
Пятое: новый analysis_runs создаётся с чистой state machine; старый ai_pipeline_runs не расширяем ещё на двадцать статусов.
Шестое: Publication создаётся только в atomic Publish transaction и с момента INSERT является immutable release snapshot.
Седьмое: Action Cases физически отделяются от Publication Action Groups. Case persistent; Group — immutable presentation projection конкретной Publication.
Восьмое: Dashboard читает только publication projections, не live Factual API.
Девятое: Chat читает Factual API + Publication и не имеет собственного SQL analytics engine.
Десятое: evaluation использует тот же runtime, но физически не имеет права Publish.
Одиннадцатое: Redis, MinIO и OpenAI никогда не участвуют внутри DB Publish transaction.
Двенадцатое: legacy после cutover удаляется физически — не остаётся режимов legacy/unified, fallback или dual read.
