
Да. После Capability Model у нас появился почти весь фундамент, чтобы правильно спроектировать Internal Canonical Factual API.
Здесь я предлагаю зафиксировать одну ключевую мысль:
Internal Canonical Factual API — единственная разрешённая точка чтения бизнес-фактов Aivion для Dashboard, Chat, Discovery, Evidence и всех будущих аналитических consumers. Никто выше этого слоя не знает таблиц UCDM, SQL, provider pagination, revision logic или того, как выбирать “правильный” Stock snapshot.
При этом я не предлагаю делать отдельный микросервис. Для текущего Aivion это должен быть типизированный Go application layer внутри backend. Если когда-нибудь архитектура действительно разделится на сервисы, поверх него можно добавить gRPC/HTTP adapter, не меняя бизнес-контракт.

1. Зачем вообще нужен Factual API
Сейчас после UCDM мы потенциально можем написать:
SELECT ...
FROM fact.sales_sku_daily
JOIN fact.stock_snapshot_positions ...
JOIN ...
прямо внутри Dashboard.
Потом отдельно другой SQL внутри Chat.
Ещё один — для Discovery.
Ещё один — для Evidence.
И через несколько месяцев получим четыре разных определения:
current stock
current category
7d sales
advertising spend
finance expense
Именно этого мы должны избежать.
Правильная схема:
                      UCDM
                       │
                       ↓
             Internal Factual API
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
    Dashboard         Chat        AI pipeline
                                     │
                              ┌──────┴───────┐
                              ↓              ↓
                          Discovery       Evidence

2. Factual API — semantic firewall
Он отвечает не просто:
какая строка лежит в PostgreSQL?
А:
какой canonical fact является правильным для этого seller, entity, периода и factual universe?
Например consumer спрашивает:
GetCurrentStock(SKU 417)
Factual API сам должен:
понять seller;
получить Read Context;
проверить capability;
выбрать последний COMPLETE Stock Snapshot, разрешённый данным context;
исключить overlapping inventory pools;
корректно просуммировать sellable stock;
сохранить NULL ≠ 0;
вернуть freshness/as-of;
вернуть coverage/limitations;
при необходимости дать ссылку на provenance.
Consumer вообще не должен знать, что существуют:
stock_snapshot_runs
stock_snapshot_positions
inventory_pools

3. И особенно AI не должен знать SQL
Никаких:
AI → SQL → canonical DB
даже read-only.
И никаких generic:
POST /facts/query
{
  "table": "...",
  "group_by": "...",
  "formula": "..."
}
Это постепенно превратится в SQL через JSON.
Правильно:
GetSKUDemand(...)
GetCurrentSKUStock(...)
GetSKUPrice(...)
GetCampaignPerformance(...)
GetSKUQueryPerformance(...)
...
То есть API отражает business semantics, а не структуру PostgreSQL.

4. Архитектурно это не HTTP API
Внутри backend я бы сделал примерно:
internal/factualapi
с Go interfaces.
Например:
type SalesReader interface {
    GetAccountDemand(ctx context.Context, req AccountDemandRequest) (AccountDemandResult, error)
    BatchGetSKUDemand(ctx context.Context, req BatchSKUDemandRequest) (BatchSKUDemandResult, error)
}
А не:
HTTP → localhost → HTTP → factual service
Причины:
backend сейчас один;
нет реальной независимой service scaling requirement;
не нужен network hop;
не нужен второй auth layer;
не нужен отдельный deployment;
compile-time Go types гораздо полезнее.

    ├── Dashboard Application Service

6. Главный объект — FactualReadContext
Любой запрос фактов должен выполняться не просто для seller, а внутри определённого factual context.
Например:
type FactualReadContext struct {
    SellerAccountID int64

    AnalysisDate    date.Date
    CutoffAt        time.Time

    TemporalPolicyVersion string
    CapabilityPolicyVersion string

    FactualUniverseID   *int64
    FactualUniverseHash string

    Mode ReadMode
}

7. Зачем нужен Read Context
Допустим Discovery стартовал:
20 Aug 05:40
В этот момент:
Stock snapshot = 05:35
Search through = 17 Aug
Finance through = 18 Aug
В 05:50 появился:
новый Stock snapshot.
Evidence спрашивает Stock.
Без Context получим:
Discovery → Stock 05:35
Evidence → Stock 05:50
То есть AI анализирует две разные реальности.
С Context:
cutoff = 05:40
Evidence всё равно получает snapshot 05:35.

8. Два режима Read Context
Я предлагаю только два.
SEALED_UNIVERSE
Для:
Discovery
Evidence
Deep Analysis
Publication
historical publication replay
Обязательно привязан:
Factual Universe Manifest ID
После seal изменить нельзя.

LATEST_STABLE
Для:
Dashboard
interactive Chat
внутренних diagnostics
В начале operation backend фиксирует:
cutoff_at = now
и один раз resolve'ит доступные domain bindings.
Все запросы внутри operation используют этот же context.

9. Не держим длинные PostgreSQL транзакции
Можно было бы использовать:
REPEATABLE READ
и держать DB transaction весь Discovery → Evidence → Deep.
Но это плохая идея.
PostgreSQL действительно гарантирует в REPEATABLE READ, что последовательные SELECT внутри транзакции видят один snapshot, в отличие от READ COMMITTED, где каждый запрос может видеть более свежие committed изменения. PostgreSQL
Но AI pipeline может длиться минуты.
Держать DB transaction всё это время не нужно.
У нас уже сильнее business mechanism:
analysis_cutoff_at
+
append-only revisions
+
bound snapshot IDs
+
capability manifest
Поэтому DB transaction используется только внутри конкретной Factual API operation.

10. Правило AS KNOWN AT
Это один из важнейших invariants Factual API.
Для revisionable facts запрос должен читать:
latest revision
WHERE observed_at &lt;= context.cutoff_at
Например Sales:
19 Aug:

rev1
100 units
observed 20 Aug 05:00

rev2
105 units
observed 20 Aug 08:00
Context:
cutoff = 06:00
ответ:
100
Не:
105

11. То же для Canonical mappings
Например 20 августа SKU был:
UNMAPPED
21 августа Category taxonomy обновилась и удалось resolve его.
Старая Publication 20 августа всё равно должна увидеть:
UNMAPPED.
Не сегодняшнее улучшенное mapping.
Иначе publication перестанет быть воспроизводимой.

12. API никогда не принимает business_date там, где нужен snapshot
Например:
GetStock(
    sku,
    date = 2026-08-19
)
я бы запретил.
Потому что Stock — не daily fact.
Правильно:

или:

Это защищает Temporal Framework непосредственно через API contract.

13. И наоборот для Sales
Sales получает:

не:

Например:
type Period struct {
    From date.Date
    To   date.Date
}
Обе границы inclusive.

14. Standard Period References
Consumer не должен самостоятельно считать:

today - 13
Для стандартной аналитики:

Например:

15. Explicit Period тоже разрешён
Например Chat спрашивает:

Тогда:

  from: 1 Aug
  to: 15 Aug
}
Но только если конкретная metric supports эту period semantics.
Например Sales — да.
Search unique users — только через direct-period source.
Stock — нет.

16. Самая важная защита: aggregation policy
Factual API знает из Metric Registry:

→ SUM_SAFE

→ DIRECT_PERIOD

→ DIRECT_PERIOD

→ SNAPSHOT_ONLY

→ DIRECT_PERIOD

→ DERIVE_FROM_COMPONENTS
Поэтому consumer не может запросить:

36. Pagination — обязательно с первого дня
Коллекции SKU, postings, finance lines, Search Query могут расти сильно.
Google API guidance рекомендует page_size/page_token изначально для List methods и opaque next_page_token, а Microsoft также рекомендует server-side pagination с самого начала, поскольку добавление её позже становится breaking change. google.aip.dev
Поэтому каждый потенциально большой List:
items
next_page_token

37. Page Token должен быть opaque
Не:
page=17
offset=1600
а:
eyJ...
Token внутри может содержать:
read_context_hash
filter_hash
ordering
last_sort_key
last_entity_id
и быть подписан backend.
Consumer его не разбирает.

38. Token привязывается к Read Context
Нельзя:

context cutoff = 05:40

page 2
latest cutoff = 05:50.
Page token содержит context identity/hash.
Если context другой:
PAGE_TOKEN_CONTEXT_MISMATCH.

39. Ordering deterministic
Каждый List имеет default order.
Например SKU:
canonical_sku_id ASC
Finance:
business_date DESC
id DESC
Search Queries:
provider ranking
then canonical_query_id
Всегда tie-breaker.

40. Не делаем arbitrary order_by
Сортировка может быть дорогой, особенно совместно с pagination; API guidance прямо рекомендует поддерживать произвольную сортировку только при реальной необходимости. GitHub
Поэтому:
SortMode
с закрытым allowlist.
Например:
BY_ORDERED_AMOUNT_DESC
BY_PAID_SPEND_DESC
BY_STOCK_ASC
только если это factual-safe и реально нужно consumer.

41. Filters тоже закрытые и типизированные

42. Batch APIs обязательны
Целевая аудитория:

Google API guidelines отдельно выделяют Batch methods после стандартных Get/List как нормальную оптимизацию. google.aip.dev

Архитектурный контракт Internal Canonical Factual API
Я предлагаю зафиксировать его так:
Internal Canonical Factual API Aivion является единственным типизированным application-level read contract над UCDM для всех бизнес-consumers. Dashboard, Chat, Discovery, Evidence и будущие analytical services не имеют прямого доступа к factual SQL/repositories. В текущей архитектуре Factual API реализуется как in-process Go service layer, а HTTP/gRPC являются только optional adapters и не образуют отдельный microservice.
Каждое чтение выполняется внутри immutable FactualReadContext, который фиксирует seller, analysis date, knowledge cutoff, Temporal/Capability Policy и при AI-run — sealed Factual Universe Manifest. Period facts, snapshots, events и versioned states разрешаются согласно их собственной temporal semantics; API никогда не подменяет snapshot business date, не использует current state для historical query и не показывает revisions, observed после context cutoff.
API contracts являются business-semantic и typed: Sales, Stock, Price, Advertising, Funnel, Finance, Search, Promotions, Account Health и Supply имеют собственные explicit methods. Generic SQL/EAV query, arbitrary metric aggregation и generic SUM/AVG API запрещены. Metric Registry определяет допустимые temporal/entity aggregations; non-additive metrics нельзя агрегировать вне разрешённой semantics.
Missing, Known Zero, Unavailable, Unknown, Not Applicable и No Denominator различаются в API contract. Capability unavailability является нормальным factual result, а не transport/application error. Каждый result может содержать readiness, temporal/as-of metadata, semantic/entity coverage, limitations и opaque FactRef для provenance. Derived facts используют versioned deterministic formulas и могут быть traced до входных facts и provider sources.
Все большие collections имеют server-side cursor pagination с opaque context-bound tokens, deterministic ordering и configurable limits. Batch methods обязательны для SKU/campaign workloads и не реализуются через N+1. Filters и sorting являются закрытыми typed allowlists, а не произвольным SQL-like expression.
Factual API не содержит AI interpretation: в нём отсутствуют concepts “problem”, “opportunity”, “critical SKU”, “bad campaign”, “optimal price”, “revenue at risk”, “health score” или recommendation. Он предоставляет исключительно source-backed canonical facts, deterministic safe projections и declared limitations. Cross-domain composite methods допустимы только для заранее утверждённых deterministic formulas вроде Stock Coverage и Advertising Spend Share.
Seller isolation является частью Read Context и repository queries; PII не включается в factual DTO. Sealed-context results детерминированно cacheable по universe hash + operation + request hash. Observability строится через OpenTelemetry spans/metrics с ограниченной cardinality.
Продуктовых вопросов у меня здесь не возникло
Есть implementation-параметры — batch sizes, page sizes, cache TTL для live context, query timeout, конкретная Go decimal-библиотека, — но это не продуктовые решения и их лучше подобрать после profiling.
То есть Internal Canonical Factual API можно фиксировать как следующий закрытый архитектурный блок.
Дальше по нашему плану уже логично проектировать Data Quality / Readiness Model. После него — Entity Landscapes, где впервые начнём превращать все эти правильные факты в компактное представление кабинета для первого AI-вызова.
