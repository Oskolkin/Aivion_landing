
Ключевой принцип всего блока:
Analysis Run — это возобновляемый, идемпотентный технический workflow. Publication — только результат полностью успешного Run. Любой crash, retry или повторная доставка job не должен приводить к повторному анализу уже завершённых стадий, смешиванию разных factual universes или частичной публикации.

1. Общая архитектура orchestration
Физически я предлагаю оставить существующий стек:
PostgreSQL
    =
source of truth состояния workflow

Redis / Asynq
    =
очередь выполнения отдельных stages

Worker
    =
исполнитель stages

MinIO
    =
immutable stage artifacts

OpenAI Responses API
    =
только Discovery и Deep
Я не рекомендую сейчас добавлять Temporal, Step Functions или отдельный workflow-service.
Причина не в том, что такие системы плохие. Наоборот, durable workflow-системы хорошо решают retries и recovery. Но нам уже хватает PostgreSQL для durable state и Asynq для at-least-once execution. Ключевое требование — каждый stage должен быть идемпотентным и resumable. Современные рекомендации по distributed workflows исходят именно из того, что task может выполниться больше одного раза; retries должны быть bounded, а операции — идемпотентными. AWS Документы

3. Scheduler не определяет, готовы ли данные
У нас уже принято:
clock ≠ readiness
Поэтому Scheduler делает только:
«пора проверить, можно ли анализировать seller».
Например после нашего not-before около окончания ежедневного ingestion window он запускает Analysis Eligibility Evaluation.
Но он не говорит:
сейчас 00:05, значит данные за вчера готовы.
Решение принимает:
AnalysisDateResolver
+
DataQuality / Readiness

4. Как определяется analysis_date
Уже принято правило:
последний полностью пригодный Core Sales business date, не позже вчерашнего дня.
Например сегодня 21 августа.
Проверяем:
20 Aug → READY?
Если да:
analysis_date = 20 Aug
Если нет:
19 Aug → READY?
и так до последнего корректного дня.
Но fallback на старый день не означает, что обязательно создаётся новая Publication.
Если current Publication уже:
analysis_date = 19 Aug
universe_hash = ABC
и новый candidate для 19 августа также:
universe_hash = ABC
то:
NO_OP

10. analysis_cutoff_at означает «что Aivion знал»
Это не:

Это:
факт был известен Aivion к 05:43.
Например Ozon завтра сообщил корректировку продажи за 15 августа.
Она относится к:

Она не должна появиться в Universe 21 августа.
Она попадёт в следующий Universe.
Так обеспечивается историческая честность Publication.

А вот если Manifest невозможно построить из-за corrupted canonical state:

21. Mandatory Action Continuity
Теперь это обязательная часть orchestration.
Из:
base_publication_id
извлекаются все atomic Action Proposals предыдущей current Publication.
Например:
12 Actions.
Создаётся:
Continuity Revalidation Set = 12
Все двенадцать должны быть переоценены новым Deep.

22. Continuity не конкурирует с Fresh Materiality
Materiality теперь фактически получает:
MANDATORY CONTINUITY TARGETS
+
FRESH MATERIALITY CANDIDATES
Например:
previous Actions:
SKU1
SKU2
Campaign7

fresh Materiality:
SKU5
SKU8
Category3
Campaign12
Deep должен видеть оба набора.

23. Очень важный budget invariant
Поскольку все прошлые Actions обязательны для revalidation:
max_atomic_actions_per_publication
&lt;=
continuity_capacity
должно быть hard invariant.
Мы не можем вчера позволить AI опубликовать 100 Actions, а сегодня сказать:
в Deep помещается только 30, остальные не проверили.
Это архитектурная ошибка конфигурации.

24. Если invariant неожиданно нарушен
Например из-за бага прошлой версии:
previous atomic Actions = 53

continuity max = 40
Я бы не выбрасывал 13 случайных Actions.
Run:
FAILED_TERMINAL
CONFIGURATION_INVARIANT_VIOLATION
и требует инженерного исправления.
Тихое dropping здесь гораздо опаснее.

25. Discovery всё равно выполняет роль breadth analysis
Mandatory Continuity target не означает:
Discovery должен обязательно создать по нему Thread.
Discovery получает информацию, что объект участвует в continuity context.
Но сама mandatory revalidation прошлого Action не зависит от Discovery Thread creation.
Иначе Discovery случайно не создаст Thread — и Action останется непроверенным.

26. Evidence имеет два происхождения
Мы уже расширили контракт:
DISCOVERY_REQUESTED

CONTINUITY_REQUIRED
Discovery-requested Evidence отвечает:
что нужно для исследования новых Threads.
Continuity-required отвечает:
что обязательно нужно для проверки вчерашних Actions.

27. Continuity Evidence строится автоматически
Например вчера был:

29. Но concurrency bounded
Нельзя:

То же касается OpenAI across sellers.

30. Discovery Pack строится immutable
На этой стадии создаём:
discovery-pack.json
и фиксируем:

После этого DISCOVERY_AI attempt никогда не получает немного другой Pack.

31. Discovery AI retry
Если OpenAI отвечает:
429
timeout
5xx
network transient
делаем bounded retries с exponential backoff + jitter.
Это стандартный resilience pattern: transient failures стоит retry'ить с увеличивающейся задержкой, но количество retries должно быть ограничено, иначе retry storm только усугубит проблему. AWS Документы

32. Не retry'им всё подряд
Например:
invalid local configuration
unknown prompt version
broken schema
factual universe mismatch
не исправится через 30 секунд.
Это:
FAILED_TERMINAL.
Fail fast.

33. Structured Outputs не отменяет application validation
Discovery и Deep используют strict Structured Outputs.
Это гарантирует структурное соответствие JSON Schema, но не истинность значений внутри результата. OpenAI прямо отмечает, что Structured Outputs не исключают содержательных ошибок модели, а также могут не дать нормальный schema-result при отказе или преждевременном завершении generation. OpenAI
Поэтому:
provider schema
↓
our technical validator
↓
business-contract invariants
всё равно обязательны.

34. Invalid AI output
Например Deep вернул schema-valid JSON, но:
Action references nonexistent SKU
или:
previous Action 7 was not assessed
Output invalid.
Мы не repair'им его.
Возможен bounded full rerun:
same Pack
same Prompt
same Schema
same model policy

35. Retry не использует предыдущий ответ
По нашему уже принятому решению:
previous_response_id = null
каждый attempt stateless.
Attempt 2 не получает:
Вот ошибки attempt 1, исправь.

36. Все AI Attempts сохраняются
Например:

→ timeout

Discovery Attempt 2
→ invalid semantic references

Discovery Attempt 3
→ valid
Сохраняем все три.

37. Я бы не делал silent model fallback v1
Например:
primary model unavailable
→ автоматически использовать другую модель

Это улучшает воспроизводимость.

41. Revalidation outcomes
Мы уже согласовали:
FULLY_SUPPORTED

PARTIALLY_SUPPORTED

NOT_SUPPORTED

UNVERIFIABLE

SUPERSEDED
Orchestrator не принимает это решение.
Он только проверяет полноту и применяет deterministic reconciliation.

42. FULLY_SUPPORTED
same Action Case
+
new Action Proposal
Например:
yesterday:
replenish 120

today:
replenish 150
Required basis тот же.
Case остаётся.

43. PARTIALLY_SUPPORTED
Хотя Action Type может совпасть, старый occurrence не переносится.
Если Deep всё ещё рекомендует действие, но уже на новом наборе оснований:
old Case → close BASIS_CHANGED
new Case occurrence → OPEN

44. NOT_SUPPORTED
old Case
→ system resolved

Action отсутствует
в новой Publication.
После этого применяется recurrence suppression policy.

45. UNVERIFIABLE
Например required Stock data отсутствует.
По принятому правилу:
показываем только Actions, у которых все основания актуальны.
Поэтому:
Action отсутствует
в новой Publication.
Но Case:
SUSPENDED_UNVERIFIED
а не resolved.
Когда capability возвращается, Case должен быть revalidated снова.

46. SUPERSEDED
Старое действие заменено другим.
Например:
decrease price
→ superseded

increase price
→ new Action.
Cooldown не применяется.

47. User DONE
DONE означает:
конкретный occurrence пользователь считает выполненным.
Но current Deep всё равно revalidate'ит его.
Если факты по-прежнему дают:
FULLY_SUPPORTED
создаём новый Action Case occurrence сразу.
Без cooldown.
То есть менеджер не может случайным DONE скрыть объективно существующую рекомендацию.

48. User DISMISSED / «Неактуально»
Наше последнее решение:
same business action identity
→ suppression 30 календарных дней.
Deep всё равно может анализировать ситуацию и даже сформировать Action Proposal.
Но deterministic Action Eligibility Policy перед Publication говорит:
SUPPRESSED_BY_USER
until 2026-09-20
И Action не попадает в visible current Action Snapshot.

49. Почему suppression применяется после Deep, а не до него
Это важный нюанс.
Если вообще не показывать entity AI на 30 дней:
мы потеряем Findings и понимание ситуации.
Правильнее:
AI reasoning
→ происходит честно

Action visibility
→ регулируется product policy.
Backend не говорит AI:
притворись, что проблемы нет.
Он говорит:
это Action сейчас не показываем пользователю.

50. Противоположный Action не suppress'ится
Если пользователь отклонил:

на 30 дней,
а Deep через неделю рекомендует:
PRICE INCREASE
это другая intent_signature.
Показываем сразу.

85. Transactional Outbox
После commit нужно:
invalidate cache
notify frontend
warm current projections
update Chat cache
emit metrics/events.
Нельзя делать это перед commit.
И нельзя полагаться на:
COMMIT
then Redis publish
без защиты: процесс может умереть между этими двумя действиями. Transactional Outbox сохраняет business changes и event-intent в одной транзакции, после чего worker доставляет событие отдельно; consumer должен быть идемпотентным. Microsoft Learn

Рекомендуемый нормативный контракт для ТЗ
Daily Analysis Aivion реализуется как durable, stage-based, resumable state machine. PostgreSQL является единственным source of truth состояния Runs/Stages; Redis/Asynq используется как at-least-once execution transport. Каждый stage обязан быть идемпотентным либо иметь явно определённую bounded retry semantics. Crash/restart не создаёт новый logical Run и не приводит к повторному выполнению уже зафиксированных успешных стадий.
Scheduler только инициирует readiness evaluation. analysis_date определяется Data Quality/Readiness Resolver как последний допустимый Core-ready business date. Analysis Run создаётся только после выполнения hard eligibility gates. До первой стандартной генерации требуется минимум 14 полных дней Core Sales Demand.
В начале Run фиксируется base_publication_id, после чего создаётся immutable Factual Universe Manifest с analysis_cutoff_at. Все downstream stages используют исключительно этот sealed universe. После sealing Analysis Run не выполняет live Ozon/provider reads; новая ingestion activity не изменяет текущий Run и может повлиять только на следующий Factual Universe.
До AI-вызовов выполняется no-op detection по factual universe и effective analysis contract. Повтор scheduler/recovery не является основанием для нового AI result. Policy/model changes могут привести к анализу того же universe только через explicit versioned reanalysis intent.
Все atomic Actions предыдущей current Publication образуют Mandatory Continuity Revalidation Set и гарантированно переоцениваются в следующем Deep Analysis. Continuity entities не конкурируют с fresh Materiality за один selection budget. Максимальное количество публикуемых Actions обязано быть совместимо с guaranteed continuity capacity.
Evidence Expansion объединяет DISCOVERY_REQUESTED и CONTINUITY_REQUIRED Evidence, но остаётся AI-free, provider-free и deterministic. Deep является вторым и финальным AI-вызовом и одновременно формирует новый semantic result и выполняет 100% revalidation предыдущих Actions.
Discovery и Deep используют immutable packs, strict Structured Outputs и bounded full retries. Retry одного AI stage всегда использует тот же Pack/Prompt/Schema/Model Policy, не использует previous_response_id и не выполняет semantic repair. Все attempts сохраняются; только один validated attempt принимается downstream.
Action reconciliation выполняется после validated Deep как deterministic plan и не мутирует application state до финального publish. FULLY_SUPPORTED reaffirm'ит Case; PARTIALLY_SUPPORTED не переносит старый occurrence; NOT_SUPPORTED системно разрешает Case; UNVERIFIABLE временно скрывает Action, не считая его решённым; SUPERSEDED заменяет его новым action intent. User DONE не suppress'ит последующий objectively supported occurrence; user DISMISSED suppress'ит same business action identity на 30 календарных дней.
Publication Candidate, Action Reconciliation Plan и required Projections полностью строятся и валидируются до мутации current product state. Publication, Action Case mutations, current-publication pointer, release ledger и outbox intent применяются одной короткой PostgreSQL transaction. Техническая partial publication запрещена.
После commit downstream cache/UI/notification operations выполняются через idempotent transactional-outbox processing. Их failure не отменяет успешно опубликованную Publication.
Для одного seller одновременно допускается не более одного active production publishing Run. Evaluation Runs могут существовать отдельно, но не меняют current Publication или Action Cases. Старый Run не может сделать себя current поверх более нового valid Publication; такой candidate завершается как STALE.
Orchestration layer не рассчитывает business significance, не создаёт Findings/Recommendations/Actions, не меняет AI decisions и не repair'ит semantic output. Его ответственность ограничена последовательностью стадий, frozen inputs, retries, idempotency, completeness, concurrency, publication atomicity и recovery.
На мой взгляд, продуктовых вопросов в этом блоке больше не осталось: твои предыдущие решения уже позволяют однозначно спроектировать lifecycle. Следующий логичный этап после утверждения этого блока — Dashboard Contracts, где мы уже пройдёмся по Overview / Funnel / Stock / Advertising / Categories / SKU / Actions и для каждого блока определим точный источник, поля, AI/factual ownership, состояния unavailable/partial и поведение Action Groups.
