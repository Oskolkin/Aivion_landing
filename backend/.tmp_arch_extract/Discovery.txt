Здесь мы уже переходим непосредственно к первому AI-вызову новой архитектуры, поэтому я бы зафиксировал контракт особенно жёстко: Discovery должен получить достаточно фактов, чтобы увидеть значимые бизнес-ситуации, но не получить свободу самостоятельно искать данные, менять factual universe или сразу выдавать финальные Actions.
Актуальный Responses API хорошо подходит под такой подход: Structured Outputs позволяют жёстко ограничить ответ JSON Schema, причём в отличие от обычного JSON mode гарантируется соответствие поддерживаемой схеме; OpenAI рекомендует использовать Structured Outputs там, где это возможно. После всех принятых нами решений pipeline становится:

  ↓

  ↓
Factual API
  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓
DEEP ANALYSIS PACK
  ↓
AI CALL #2 — DEEP ANALYSIS
  ↓

Discovery отвечает только на два вопроса:
Какие ситуации действительно заслуживают углублённого анализа?
И:
Какие дополнительные факты нужно раскрыть, чтобы качественно разобраться в каждой из этих ситуаций?
Он не отвечает:
Что нужно сделать продавцу?
и не должен окончательно отвечать:
Почему это произошло?

4. Почему Discovery не должен сам ходить за данными
Иначе архитектура:

Например Discovery запустился:

а в 05:50 AI через tool запросил:

Мы снова нарушили бы фундаментальный invariant:

Поэтому AI может только написать:

Но сам Evidence он не получает в этом вызове.

29. Discovery Constitution
В stable prompt я бы зафиксировал примерно такие правила:
анализируй только факты, находящиеся в Discovery Pack;
можешь использовать общие знания marketplace-бизнеса для интерпретации, но не придумывай seller-specific факты;
не считай отсутствующие данные нулём;
обязательно учитывай readiness, coverage, lag и temporal windows;
Sales Demand является владельцем заказанного спроса;
Advertising attribution и Search attribution не прибавляются к Sales;
Finance accrual не является Sales revenue/profit;
Supply inbound не является Stock;
promotion action price не является current Price;
Funnel surfaces не образуют автоматически линейную cohort funnel;
совместные изменения не доказывают causality;
provider statuses являются provider judgements;
рассматривай как положительные, так и отрицательные изменения;
не обязан создавать Thread для каждой Material Entity;
разрешено вернуть ноль Threads;
группируй связанные observations, не создавай дублирующие Threads;
не выдавай финальные причины;
не выдавай Actions;
не выдавай рекомендации;
не выбирай final priority seller actions;
запрашивай только Evidence из Evidence Menu;
Evidence запрашивай только если оно действительно помогает разобраться в Thread.
Это фактически AI constitution Stage 1.

30. Почему stable prompt лучше держать отдельно от Pack
Во-первых, он versioned.
Во-вторых, его можно одинаково использовать для всех sellers.
В-третьих, это хорошо сочетается с prompt caching. В актуальной API документации OpenAI для GPT-5.6+ caching работает по точному совпадению prompt prefix; можно поставить explicit breakpoint после стабильных инструкций, а динамический seller payload передавать после него. Платформа OpenAI
То есть структура:
STABLE DISCOVERY INSTRUCTIONS
[cache breakpoint]

DYNAMIC DISCOVERY PAYLOAD
Но cache остаётся только оптимизацией.
Correctness от cache никак не зависит.

31. Discovery Pack должен быть bounded по токенам
Очень важное правило:
Мы никогда не рассчитываем на то, что OpenAI сам что-нибудь отрежет.
Responses API поддерживает truncation, причём текущий API позволяет явно держать truncation disabled; для Aivion я рекомендую всегда использовать именно это поведение. OpenAI Developers
Если Pack не помещается:
PACK_TOO_LARGE
И backend должен перестроить Pack детерминированно.
Не:
отрежем последние 30 000 символов JSON.

35. Почему компактность важна даже при большой context window
Дело не только в стоимости.
Исследование Lost in the Middle показало, что long-context models не всегда одинаково хорошо используют информацию в разных частях большого контекста; качество может снижаться, когда релевантные сведения теряются внутри длинного входа. arXiv
Поэтому:
Materiality + Landscapes
не просто optimization.
Это часть качества анализа.

И всё.

38. Очень важно разрешить NO_MEANINGFUL_THREADS
Materiality говорит:

Но это не значит:

Discovery должен иметь право сказать:

которая заслуживает углубления.
Без этого мы искусственно заставим модель каждый день выдумывать проблемы.

43. Как выбирается Primary Entity
AI выбирает entity, которая лучше всего выражает scope ситуации.
Например:
Массовое движение нескольких SKU одной категории
primary = CATEGORY
Локальный отдельный товар
primary = SKU
Advertising-specific pattern
primary = CAMPAIGN
Account Health / общесистемное изменение
primary = ACCOUNT

44. observation
Короткое, factual-grounded описание наблюдаемого паттерна.
Например:
Спрос SKU снизился одновременно с ростом наблюдаемой цены и ухудшением поисковой позиции.
Допустимо.
Недопустимо:
Повышение цены вызвало падение продаж.
Потому что это уже causality.

45. Я бы не заставлял модель повторять цифры в observation

123. Почему Discovery + Evidence лучше одного огромного AI-вызова
У нас получается фактически:

breadth

Call #2:
depth
Первый видит много сущностей, но компактно.
Второй видит мало ситуаций, но глубоко.
Это гораздо логичнее для seller с 2 000 SKU, чем:
все данные × все SKU × 90 дней
→ один огромный prompt.
И соответствует общей идее context engineering: deterministic работу — filtering, aggregation, routing — выгоднее выполнять вне model context, оставляя модели именно judgment/reasoning. Архитектурный контракт Discovery
Я бы зафиксировал его следующим образом:
Discovery Aivion является первым и единственным breadth-oriented AI stage новой аналитической архитектуры. Его входом является immutable bounded Discovery Pack, детерминированно построенный из одного sealed Factual Universe после Entity Landscapes и Materiality Selection. Discovery не имеет tools, network access, SQL, Factual API access или provider access и не может расширять factual universe самостоятельно.
Discovery Pack v1 передаётся как canonical structured JSON и содержит только Analysis Context, Domain Windows, analytical Capabilities/Limitations, Account Landscape, Detail Landscapes выбранных leaf Categories/SKUs/Campaigns и run-specific Evidence Menu. Materiality scores, ranking lanes, selection reasons и engineering DQ noise не передаются модели. ZIP/file transport не используется как механизм token compression; если payload превышает budget, Pack детерминированно перестраивается через versioned Detail/Materiality Budget Profiles, а arbitrary truncation запрещён.
Каждый значимый Landscape fact получает pack-local deterministic Fact Handle, отображаемый модели рядом со значением. Отдельный immutable Fact Handle Map связывает handles с Internal Factual API FactRefs, formulas и source provenance. Discovery Threads обязаны ссылаться на существующие Fact Handles, что создаёт lineage Discovery → Canonical Facts без необходимости модели повторно копировать числовые значения.
Discovery Output представляет собой упорядоченный набор Analysis Threads. Каждый Thread имеет primary main entity, optional related entities, короткое non-causal observation, investigation focus, factual basis handles и zero-or-more Evidence Requests. Primary Entity допускается только Account, seller-bearing leaf Category, SKU или Campaign. Supporting entities могут использоваться только как related context.
Discovery не возвращает problem type, opportunity type, severity, root cause, final cause, recommendation, Action, target value, expected effect, forecast или self-reported confidence. Он не обязан создавать Thread для каждой Material Entity и имеет право вернуть NO_MEANINGFUL_THREADS. Positive и negative situations рассматриваются симметрично. Совместная динамика нескольких metrics является поводом для investigation, но не доказательством causality.
Evidence Request является декларативной ссылкой на versioned closed Evidence Catalog, а не tool call. AI не определяет SQL, metric formula, arbitrary period, sorting или query parameters. Backend технически валидирует Evidence Type и entity applicability и позднее раскрывает Evidence исключительно из того же Factual Universe.
Discovery выполняется stateless через Responses API без previous_response_id; Structured Outputs со strict JSON Schema являются обязательным output contract. Backend не semantic-repair'ит ответ и не создаёт отсутствующие Threads/Evidence Requests. Invalid outputs фиксируются как failed attempt; допускается только bounded full rerun исходного Pack согласно policy, но не многоступенчатый repair loop. Exact request/output artifacts, hashes, model/prompt/schema/policy versions и token usage сохраняются для audit.
Discovery Pack является deterministic, Discovery AI output — нет. Поэтому воспроизводимость означает сохранение exact input/output и versions, а качество/стабильность AI оцениваются отдельными offline evals, а не предполагаются архитектурой.
Один продуктовый вопрос здесь всё-таки появился
Он касается сценария:
Discovery = NO_MEANINGFUL_THREADS
Я рекомендую всё равно выполнять второй Deep Analysis call, но уже без Evidence Expansion либо с пустым Evidence.
То есть:
Discovery:
NO_MEANINGFUL_THREADS

↓
Evidence:
none

↓
Deep Analysis:
Account + factual context + Discovery result

↓
Publication:
нормальный AI-вывод о состоянии кабинета,
но без искусственно придуманных проблем/Actions
Почему я это рекомендую: иначе в спокойный день у нас вообще не будет AI, который сформирует нормальное account-level резюме Dashboard. Backend же сам писать семантический текст вроде «существенных изменений нет» не должен — мы уже договорились, что interpretation принадлежит AI.
Если ты согласен с этим поведением, я бы зафиксировал Discovery Pack + Discovery Output Contract как CLOSED и следующим шагом спроектировал Evidence Catalog + Evidence Expansion — это будет одна из самых важных частей всего pipeline, потому что там нужно определить, какую именно глубину данных AI имеет право запросить по каждому Thread и как не превратить Evidence обратно в огромный Data Pack.
