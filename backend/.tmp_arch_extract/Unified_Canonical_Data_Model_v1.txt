
Главный вывод: Unified Canonical Data Model не должен быть одной огромной универсальной таблицей фактов. Это должен быть единый типизированный граф сущностей и фактов, у которого общие правила identity, времени, provenance, ownership, aggregation, missing/zero, revisions и seller isolation.
Все отдельные модели уже дают для этого достаточно прочный фундамент: SKU имеет стабильную seller-scoped identity и не смешивает metadata с бизнес-фактами; Category имеет собственную глобальную taxonomy и historical assignments; Sales разводит demand и fulfillment; Temporal Framework различает period/event/snapshot/versioned state; Stock — snapshot по inventory pools; Campaign — самостоятельная entity; Search Query — supporting entity; Promotions разделяет eligibility и membership; Supply разделяет Order/Supply/Bundle/Act; Finance — самостоятельный accrual ledger. 1. Что именно является Unified Canonical Data Model
Я предлагаю дать ему такое определение:
Unified Canonical Data Model Aivion — единая фактическая модель состояния marketplace-кабинета, состоящая из стабильных canonical entities, их исторических состояний и relations, source-backed period/snapshot/event facts, deterministic derived facts и полного provenance, позволяющего воспроизвести factual universe продавца таким, каким Aivion знал его на конкретный analysis cutoff.
Очень важно последнее:
не просто:
"что сейчас лежит в БД"

а:
"что Aivion знал
на момент T
о бизнес-состоянии,
относящемся к периоду/моменту X"
Это фактически selective bitemporal architecture: мы различаем effective/business time и record/knowledge time. Именно это классически решает проблему поздних исправлений исторических данных: сегодняшнее знание о прошлом может отличаться от того, что система знала вчера. martinfowler.com
Но делать полноценную generic bitemporal database поверх каждой строки я не рекомендую. Мы реализуем нужную семантику через наши конкретные period, effective_at, as_of_at, valid_from, observed_at, revision и analysis_cutoff_at.

12. Для version intervals вводим единое правило
Всегда:
[valid_from_at, valid_to_at)
то есть:
valid_from inclusive
valid_to exclusive
Например:
V1:
[10 Aug 10:00, 15 Aug 12:00)

V2:
[15 Aug 12:00, infinity)
Никаких вариантов, где один домен считает valid_to включительно, а другой нет.

13. Не должно быть двух одновременно активных version rows
Например SKU:
SKU 417
не может одновременно иметь:

V2 valid 15–∞
Если остаёмся на PostgreSQL 16, это можно защищать не только backend-кодом, но и tstzrange + GiST exclusion constraint. PostgreSQL прямо поддерживает range types и exclusion constraints для запрета пересекающихся интервалов. PostgreSQL
То есть для критических relation/state tables я бы реально использовал DB-level guard.

125. Предлагаемый архитектурный контракт UCDM
Я бы зафиксировал его так:
Unified Canonical Data Model Aivion является типизированным seller-isolated canonical graph, а не универсальным EAV-хранилищем. Stable business identities хранятся отдельно от mutable state; typed canonical entities имеют собственные provider-backed identity constraints, а единый EntityRef используется только как reference abstraction для AI/Evidence/Actions. Все factual domains подчиняются общему Temporal Contract и явно являются period facts, events, snapshots либо versioned states. Business/effective time и knowledge/observation time не смешиваются; revisionable provider facts сохраняют историю revisions, что позволяет воспроизводить factual state AS KNOWN AT analysis_cutoff_at. Missing никогда не превращается в zero без source semantics. Partial enumeration не используется для доказательства отсутствия entity или relation.
Каждый business fact имеет ровно одного canonical owner domain. Sales является владельцем ordered demand; Stock — текущего sellable inventory; Supply — inbound и acceptance; Price — текущей/customer-facing цены; Promotions — promotion definitions, eligibility и membership; Advertising — paid spend и provider advertising attribution; Search — query-specific provider attribution/performance; Funnel — pre-order behavioural facts; Finance — Ozon financial accrual ledger; Account Health — provider ratings и health classifications. Reconciliation между domains не создаёт новых денежных, товарных или attribution totals. Synthetic allocation по SKU/Category запрещена без explicit source semantics.
Category analytics является temporal derived projection через historical SKU→Category assignments и системную UNMAPPED; parent Category rollups не дублируют source facts. Non-additive metrics не агрегируются через SUM/AVG без зарегистрированной policy. Metric semantics, units, aggregation rules, zero/missing behaviour и deterministic formulas управляются versioned Metric/Policy registries.
Все canonical facts имеют provenance до source sync/artifact и source-contract version. Production хранит replayable sanitized source artifacts, достаточные для аудита и повторной нормализации, без ненужного PII. Source corrections могут менять current factual knowledge, но опубликованные Analysis/AI Publications immutable.
Каждый Analysis Run фиксирует immutable Temporal Context и Factual Universe Manifest: analysis_date, analysis_cutoff_at, domain readiness, выбранные complete snapshots/revisions, source/policy versions и deterministic data hashes. Discovery, Evidence Expansion и Deep Analysis работают исключительно внутри этого factual universe. SellerAIDataPack/Discovery Pack являются детерминированными проекциями UCDM, а не самостоятельными источниками истины.
Canonical layer содержит только provider facts, canonical normalization и deterministic derived facts. Он не определяет бизнес-смысл, причинность, priority или Actions. AI остаётся единственным владельцем interpretation и recommendations; разрешённые Action Targets v1 — только Account, Category, SKU и Campaign.
Вопросов, которые требуют твоего продуктового решения, сейчас нет
Я сознательно не спрашиваю тебя про TTL snapshots, глубину correction window, retention raw artifacts, partitioning, конкретную точность NUMERIC, частоту sync и подобные параметры — это implementation/operational policies, их разумнее определить на реальных данных и сделать versioned.
С архитектурной точки зрения Unified Canonical Data Model v1 я считаю спроектированным на уровне основных принципов и структуры.
Следующий шаг я бы сделал не Business Data Capabilities сразу, а сначала отдельно и очень подробно спроектировал физическую модель UCDM / Schema Blueprint: конкретный список таблиц, PK/FK/UNIQUE, common enums, relations, какие старые таблицы удаляются/мигрируют, какие views нужны, какие constraints защищают invariants и в каком порядке это внедрять в текущую БД. После такого blueprint уже можно безопасно переходить к Business Data Capabilities.
