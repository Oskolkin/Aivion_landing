
Да. После сопоставления UCDM, Temporal Framework, всех доменных моделей и актуального состояния Ozon API я бы строил Business Data Capabilities Model как отдельный системный слой между UCDM и будущим Factual API.
Его задача не ответить «работает ли API Ozon», а дать однозначный ответ:
Какие бизнес-вопросы Aivion действительно способен корректно анализировать для конкретного продавца, на конкретный момент и в конкретном Analysis Run?
Это принципиально разные вещи.
Например /v1/analytics/data может одновременно давать базовые revenue/ordered_units всем продавцам и расширенные Funnel-метрики только при Premium Plus. /product-queries без подписки возвращает часть показателей, а Premium/Premium Plus/Premium Pro расширяют набор и историю; Premium Pro отдельно открывает market Search и подробную customer price. GitHub Поэтому capability уровня «Analytics API работает» нам совершенно недостаточна.

1. Главный принцип Capability Model
Я предлагаю зафиксировать:
Business Capability — это гарантированная способность Aivion получить и корректно использовать определённый тип бизнес-фактов в определённой grain/temporal semantics, а не наличие API endpoint, подписки или строки в БД.
Например:
STOCK.CURRENT_SELLABLE
означает не:
/v1/analytics/stocks ответил 200
а:
есть полный достаточно свежий Stock Snapshot
+
SKU разрешены
+
semantics sellable_units принята
+
snapshot попадает до analysis_cutoff_at
Только тогда capability действительно usable.

Очень важно.
Один endpoint:

даёт одновременно:

FUNNEL.SEARCH_IMPRESSIONS
FUNNEL.PDP_IMPRESSIONS
FUNNEL.SEARCH_CART_ADDS
FUNNEL.PDP_CART_ADDS

Но первые возможности могут быть:

Документация подтверждает, что базовые revenue и ordered_units доступны всем продавцам, а значительная часть Funnel metrics относится к Premium Plus. GitHub
Следовательно:
endpoint capability
вообще не должно быть главным понятием Business Layer.

3. Capability ≠ подписка
Мы это уже утвердили на Funnel и Search.
Например:
seller says Premium Plus = true
ещё не означает:

Потому что возможны:
metric deprecated;
scope/role problem;
source contract changed;
request invalid;
provider malfunction;
data collection incomplete.
И наоборот, Search API прямо допускает часть показателей без Premium, хотя полная аналитика требует подписки. GitHub
Поэтому:

=
entitlement hint

live source
=
access evidence

canonical facts
=
actual data evidence

semantic contract
=

4. Capability ≠ Readiness
Это ещё одна важная граница.
Capability отвечает:
такая возможность у seller в принципе есть?
Readiness отвечает:
можно ли использовать её в этом Analysis Run?
Например:
Advertising capability:
SUPPORTED

Performance connection:
valid

historically Advertising:
works
Но сегодня API вернул 500.
Получаем:
capability structurally:
AVAILABLE

current run readiness:
FAILED
Не:
Advertising permanently unavailable.

20. Точная семантика final states
READY
Capability полностью usable в предусмотренной semantics для текущего Analysis Context.
PARTIAL
Данные можно использовать, но есть существенное ограничение:
partial entity coverage;
top-N only;
history shorter than desired;
domain lag;
some metric unavailable;
mapping coverage incomplete.
AI имеет право использовать capability только вместе с limitation metadata.
STALE
Данные существуют и были валидны, но превышают current freshness policy.
UNAVAILABLE
Capability сейчас структурно недоступна:
subscription;
scope;
provider source removed;
source contract unavailable.
FAILED
Должна была быть доступна, но текущая попытка не удалась:
5xx;
pagination failed;
processing failed;
validation failed.
NOT_APPLICABLE
Capability не имеет смысла для данного seller/context.
Например seller фактически не использует FBO:
SUPPLY.FBO_ACCEPTANCE = NOT_APPLICABLE

21. FAILED и UNAVAILABLE нельзя смешивать
Это принципиальный invariant.
Без Premium Plus:
FUNNEL.PDP_IMPRESSIONS =
UNAVAILABLE
reason = SUBSCRIPTION
Provider outage:
FUNNEL.PDP_IMPRESSIONS =
FAILED
reason = SOURCE_5XX
Это разные продуктовые ситуации.
Temporal Framework уже требует именно такое различие.

129. Архитектурный контракт, который я рекомендую зафиксировать
Business Data Capabilities Aivion является deterministic metadata-layer поверх UCDM, описывающим не API endpoints, а фактические бизнес-возможности анализа конкретного seller. Capability определяется одновременно provider contract maturity, seller access/entitlement, фактическим live source result, accepted source semantics, collection completeness, entity resolution, semantic coverage, temporal freshness/alignment, history availability и dependencies. Subscription и HTTP status являются только входными evidence и никогда самостоятельно не определяют capability.
Capability и readiness разделяются. Текущая способность получать данные может существовать при текущем FAILED collection; исторические данные могут оставаться доступными после потери подписки; beta/deprecated являются характеристиками source contract, а не readiness status. Единый run-level readiness vocabulary: READY, PARTIAL, STALE, UNAVAILABLE, FAILED, NOT_APPLICABLE. Причины хранятся отдельно и не сводятся к одному status.
Capability Model поддерживает metric-level и grain-level состояния, history segments с реальной granularity, quantitative entity/mapping coverage и semantic scopes вроде FULL или TOP_N_PROVIDER_RANKED. Transport completeness никогда не подменяет semantic completeness. Empty valid universe не считается source failure, Missing не превращается в Zero.
Capabilities формируют versioned dependency DAG. Derived/composite capabilities доступны только при готовности required dependencies и temporal/currency compatibility. Synthetic allocation, semantic inference и causal interpretation не входят в capability evaluation.
Перед Analysis Run capabilities оцениваются deterministic backend evaluator'ом без network side effects. После определения analysis_cutoff_at exact capability state замораживается в immutable Factual Universe Capability Manifest и входит в universe hash. Discovery, Evidence, Deep Analysis, Dashboard и Chat используют одну и ту же capability semantics.
Hard gate Daily Analysis v1 ограничивается usable Canonical SKU/Catalog и complete Core Sales demand/account reconciliation; остальные domains деградируют независимо и передаются как limitations. Seller API и Performance API остаются обязательными интеграционными плоскостями onboarding, но transient failure Performance/Advertising не блокирует Daily Publication.

Один продуктовый вопрос действительно появился
Он касается не архитектуры capability layer, а поведения продукта при полностью пустом или фактически неактивном кабинете.
Предлагаю такое правило:
Seller подключился
Catalog = 0 SKU
или
нет meaningful Sales history
→ не запускать дорогой Discovery/Deep Analysis и не публиковать искусственную “аналитику без данных”.
Вместо этого кабинет находится в состоянии примерно:
CONNECTED_NO_ANALYZABLE_DATA
и показывает:
Кабинет подключён, но данных пока недостаточно для анализа.
При этом ingestion/capability evaluation продолжаются, а первый AI Run автоматически запускается, когда появляется минимально достаточный factual universe.
Для нашей целевой аудитории 700–2000 SKU это кажется мне правильнее, чем генерировать AI-отчёты для пустого кабинета.
