
Исследования long-context моделей показывают, что просто увеличение объёма контекста не гарантирует качественного использования всех фактов: релевантная информация может теряться внутри большого массива данных. Практические рекомендации по context engineering поэтому делают акцент не на «положить в prompt всё», а на отборе максимально полезного контекста на каждый токен. arXiv Для Aivion это особенно важно: продавец с 2 000 SKU легко создаёт десятки тысяч canonical facts ещё до Search Queries, Finance и lifecycle.
Дополнительно актуальный Ozon API продолжает быстро меняться: Stock с 17 августа 2026 стал real-time, старые Finance transaction methods будут отключены 8 сентября 2026, а FBO Acceptance Acts появились как beta только 11 августа. Telegram Performance API также продолжает менять campaign/statistics contracts. GitHub Поэтому Landscape нельзя строить непосредственно из полей Ozon — только через уже утверждённые UCDM → Capabilities/DQ → Factual API.
1. Что такое Entity Landscape
Предлагаю такое определение:
Entity Landscape — детерминированное, компактное, типизированное представление фактического состояния и динамики конкретной основной бизнес-сущности Aivion в рамках одного immutable Factual Universe.
Основные Landscape Entities v1:
ACCOUNT
CATEGORY
SKU
CAMPAIGN
Это полностью совпадает с нашим Action Target allowlist.
При этом:
Promotion
Search Query
Posting
Order
Supply
Supply Order
Acceptance Act
Warehouse
Cluster
Product Type
Pricing Strategy
не получают равноправные самостоятельные Discovery Landscapes.
Они становятся supporting context основных сущностей.

Архитектура:

5. Landscape также не определяет Materiality
Это важная граница.
Landscape может содержать:
ordered_amount_current7 = 500 000
account_share = 12.4%
abs_delta = -150 000
Но не:
materiality_score = 87
Это следующий слой.
То есть Landscape отвечает:
«Что фактически происходит с этой сущностью?»
Materiality:
«Насколько эту сущность вообще стоит показывать Discovery?»
Discovery:
«Что это означает для бизнеса?»

6. Главное новое решение: Landscape нужен в двух уровнях
Если сделать сразу богатый Landscape по всем 2 000 SKU, мы опять создадим огромную систему.
Поэтому предлагаю:
Landscape Core
+
Landscape Detail
Landscape Core
Очень компактный.
Строится для всех потенциально анализируемых Account / Category / SKU / Campaign.
Используется прежде всего Materiality Engine.
Например SKU Core:
sales current7
sales previous7
sales delta
account sales share

stock
coverage

price/current change

ad spend
ad attributed amount

search summary state

open inbound

capability flags
Без списков Search Queries, Promotions, Supplies и Campaigns.
Landscape Detail
Строится только после того, как Materiality Engine выбрал сущность.
Содержит больше контекста:
top provider-ranked queries
promotion context
supply stage details
campaign context
price-change observations
finance breakdown coverage
funnel surfaces
Но всё равно намного компактнее Evidence.

7. Почему Detail ≠ Evidence
Допустим Materiality выбрала:
SKU 417
Landscape Detail может дать:
2 active promotions
1 open supply
3 advertising campaigns
top 3 provider-ranked search queries
Но Evidence Expansion позже может раскрыть конкретно:
все открытые Supply
их lifecycle
Acceptance Acts
30-day Stock observations
campaign history
Price observations
Search query details
Posting events
Landscape — стандартный обзор.
Evidence — глубокая динамическая выборка, зависящая от того, что Discovery решил исследовать.

10. Domain Windows храним один раз
Это очень важно из-за разных provider lag.
Например:
{
  "sales": {
    "current": ["2026-08-13", "2026-08-19"],
    "previous": ["2026-08-06", "2026-08-12"],
    "aligned_to_analysis_date": true
  },

  "search": {
    "current": ["2026-08-11", "2026-08-17"],
    "previous": ["2026-08-04", "2026-08-10"],
    "aligned_to_analysis_date": false,
    "lag_days": 2
  },

  "finance": {
    "current": ["2026-08-12", "2026-08-18"],
    "previous": ["2026-08-05", "2026-08-11"],
    "lag_days": 1
  }
}
И Landscape просто ссылается:
window = SALES_CURRENT_7D
вместо повторения дат.

11. Никогда не заставляем все domains использовать один fake period
Например:

Finance:
12–18 Aug
Это нормально.
Ненормально:
Подставить Search 11–17 под label «13–19».

16. Но Landscape не маркирует направление как good/bad
Например DRR:

Потому что semantic interpretation принадлежит AI.
Исключение — provider explicit judgement.
Например Account Health:

130. Архитектурный контракт
Я предлагаю зафиксировать:
Entity Landscape Aivion является deterministic typed projection Factual Universe для одной основной AI Entity — Account, Category, SKU или Campaign. Landscapes строятся исключительно через Internal Canonical Factual API в одном sealed FactualReadContext, не обращаются к provider API, UCDM repositories или AI и не являются самостоятельным Source of Truth.
Landscape содержит factual state, standardized period comparisons, safe deterministic aggregates, current snapshot context, business exposure, capability/readiness metadata и ограниченный supporting context. Он не содержит problems, opportunities, priority, causal interpretation, semantic severity или recommendations. Provider judgements могут передаваться только с явным provider prefix.
Landscapes имеют два уровня: Core для всего eligible entity universe и Detail только для сущностей, выбранных последующим Materiality Engine. Core оптимизирован для дешёвого batch-построения и factual ranking; Detail добавляет bounded Search Query, Campaign, Promotion, Supply и другие supporting contexts, но не заменяет Evidence Expansion.
Account, Category, SKU и Campaign имеют разные typed Landscape schemas. Наличие domain block определяется фактической применимостью и capabilities; одна универсальная EAV-схема запрещена. Global Domain Windows, capabilities и limitations дедуплицируются на Landscape Set level, чтобы одинаковая metadata не повторялась для тысяч сущностей.
Сравнения используют standard Temporal semantics: current_7d vs previous_7d является основным comparable window, процентные метрики используют p.p., transition from/to zero моделируется отдельно, snapshot facts не превращаются в daily facts. Source-native lagging domains сохраняют свои собственные explicit windows и не маскируются под analysis_date.
Landscape supporting lists всегда bounded и детерминированно отсортированы, а truncation и semantic coverage явны. Supporting entities не становятся Action Targets. Landscapes rebuildable из Factual Universe + Profile Version; persistent mutable Landscape tables не создаются. Exact landscapes, вошедшие в AI input, сохраняются как immutable artifacts будущего Discovery Pack.
Один продуктовый вопрос действительно появился
Он касается Category Action Target.
Сейчас Category Model допускает Category как полноценную AI Entity/Action Target, но taxonomy Ozon иерархическая. Если создать Landscapes одновременно для:
Электроника
→ Бытовая техника
→ Кофемашины
одни и те же SKU/Sales будут повторяться на трёх уровнях. Это сильно увеличит Discovery Context и почти наверняка создаст дублирующие выводы:
проблема категории «Бытовая техника»
и рядом:
проблема категории «Кофемашины».
Моя рекомендация для v1:
Category Landscape и Category Action Target создавать только для seller-bearing leaf Category — той canonical Category, которая непосредственно назначена SKU. Parent Categories использовать исключительно как taxonomy/path context и для агрегированных навигационных представлений, но не как самостоятельный Action Target v1.
Например:
Электроника &gt; Бытовая техника &gt; Кофемашины
Action:
Category = Кофемашины
а не:
