
1. Что такое Publication в Aivion
Publication — это:
неизменяемый зафиксированный результат одного полностью завершённого анализа seller на конкретном sealed Factual Universe.
Проще:
Ozon facts
    ↓
Sealed Factual Universe
    ↓
Landscapes / Materiality
    ↓
Discovery
    ↓
Evidence
    ↓
Deep Analysis
    ↓
Validated Findings / Recommendations / Actions
    ↓
PUBLICATION
После того как Publication создана, её содержимое никогда не редактируется.
Например:
Publication #108
analysis_date = 2026-08-20

Finding:
SKU 417 sales -32%

Recommendation:
пополнить запас

Action:
SKU 417 → replenish
Даже если 21 августа Ozon пересчитал исторические данные, Publication #108 остаётся такой, какой была 20 августа.
Новые правильные данные дадут:
Publication #109
а не переписывание #108.

2. Publication ≠ Analysis Run
Это принципиальное разделение.
Analysis Run — технический процесс:
RUNNING
Discovery failed
retry
Evidence completed
Deep failed
retry
...
Он может:
падать;
повторяться;
иметь attempts;
быть aborted;
никогда не стать публикацией.
Publication появляется только после полного успешного прохождения pipeline.
Поэтому я бы не делал:
publication.status = BUILDING
publication.status = DEEP_RUNNING
publication.status = FAILED
Это состояния Analysis Run, а не Publication.
Правильнее:
Analysis Run
    ↓
validated release candidate
    ↓
atomic publish
    ↓
Publication
То есть само наличие записи Publication уже означает:
данный результат успешно опубликован.

3. Нельзя публиковать «частично готовый анализ»
Например:
Discovery ✅
Evidence ✅
Deep ✅
Actions ✅
Overview Projection ✅
Stock Projection ✅
Advertising Projection ❌
Publication не должна становиться current.
Предыдущая Publication остаётся доступной.
Никакого состояния:
Новый AI-анализ уже появился на Overview, но Advertising пока старый.
Это сразу возвращает нас к несогласованному продукту.
При этом PARTIAL внутри business domain допустим.
Например:
Search = PARTIAL
Finance = UNAVAILABLE
Funnel = UNAVAILABLE
это нормальная Publication, потому что Deep анализировал именно такую capability picture.
Разница:
DOMAIN PARTIAL
= корректно известное ограничение данных

PUBLICATION PARTIAL
= технически недособранный продукт
Первое разрешено.
Второе запрещено.

5. Publication Identity
Минимум:
publication_id

seller_account_id

publication_generation

analysis_date

analysis_cutoff_at

published_at

102
103
...
Он не является analysis_date.
Потому что для:

теоретически может существовать:
Publication 108
Publication 109
если появился новый factual cutoff или был осознанный reanalysis с новой policy.

Publication должна точно знать:
factual_universe_manifest_id
factual_universe_hash
Иначе через полгода мы не сможем ответить:
На каких именно данных AI сделал этот вывод?
Из Publication:

↓
Factual Universe FU-891
↓
Fact Handle
↓

7. Publication не должна копировать в себя всю UCDM
Мы не складываем внутрь Publication:
90 дней Sales всех 2000 SKU
все Stock snapshots
все Finance lines
...
Publication хранит ссылку на sealed universe и необходимые immutable artifacts.
То есть:
UCDM
= factual source of truth

Publication
= immutable result анализа
Они не дублируют друг друга.

Например:
factual_api_contract_version

materiality_budget_version

Почему это важно?
Потому что результат:
Publication #108
определяется не только данными.
Он определяется:
данные
+
наши deterministic policies
+
AI prompts/models/contracts
Через год мы должны понимать, какой именно алгоритм сформировал Publication.

9. Publication content hash
После нормализации всей canonical Publication:
canonical serialization
↓
SHA-256
↓
publication_content_hash
Хэш нужен для:
аудита;
no-op detection;
idempotency;
integrity;
artifact validation.
Если один и тот же publish process запустился повторно после crash, он не создаёт новую Publication с тем же canonical content.

10. «Current Publication» — отдельный pointer
Я категорически не рекомендую искать current publication так:
ORDER BY published_at DESC LIMIT 1
Нужен явный:
seller_current_publication
Например:
seller_account_id = 1
publication_id = 108
generation = 108
updated_at = ...
Это единственная точка, определяющая:
Какой аналитический snapshot сейчас является текущим для seller.

11. Зачем отдельный pointer
Представим одновременно работают два Runs:
Run A
analysis cutoff = 06:00

Run B
analysis cutoff = 08:00
B закончил первым:
Publication 109
Потом A наконец заканчивается.
Мы не должны позволить A сделать себя current поверх более нового B.
При publish backend проверяет:
candidate chronology
vs
current pointer
и отклоняет:
STALE_PUBLISH_CANDIDATE

12. Ordering публикаций
Обычная логика:
более поздний analysis_date
&gt;
более ранний

при одинаковом analysis_date:
более поздний valid analysis_cutoff
&gt;
более ранний
Осознанный reanalysis по новой analysis policy/model должен идти отдельным явным режимом.
Нельзя случайно заменять current Publication только потому, что OpenAI во второй раз сформулировал ответ немного иначе.

13. Same universe + same policies = не публикуем заново
Например:
FU hash = ABC

Materiality policy = 7
Discovery = 4
Evidence = 2
Deep = 5
Action Catalog = 1
И current Publication уже построена именно на этой комбинации.
Scheduler случайно запускает анализ снова.
Результат:
NO_OP_ANALYSIS
а не новая Publication.
AI недетерминирован, но это не причина ежедневно перегенерировать один и тот же factual state.

14. Model upgrade — отдельный случай
Например:
deep_model_policy_v5
→
deep_model_policy_v6
Технически тот же factual universe может быть проанализирован заново.
Но это должно быть явное действие rollout/reanalysis policy, а не случайная публикация.

15. Что именно immutable
Immutable:
Publication canonical content
Factual Universe reference
Deep result
Findings
Recommendations
Action proposals
projection snapshot published at that time
analysis versions
hashes
Mutable отдельно:
current publication pointer
Action Case user state
current Action view
visibility/control state
Не смешиваем их.

16. Publication visibility/control не должна менять содержимое
Иногда может понадобиться:
снять ошибочную Publication с current.
Например обнаружили баг в projection или severe analysis defect.
Не делаем:
UPDATE publication
SET findings = ...
Вместо этого нужен control plane:
publication_release_events
Например:
PUBLISHED
MADE_CURRENT
SUPERSEDED_AS_CURRENT
WITHDRAWN
ROLLBACK_ACTIVATED
Сам Publication content остаётся неизменным.
Это схоже с преимуществом immutable history: исходная запись остаётся для аудита, а последующие состояния добавляются отдельно. При этом я не предлагаю переводить весь Aivion на Event Sourcing — Microsoft отдельно подчёркивает, что полноценный Event Sourcing добавляет существенную сложность и оправдан не везде. Нам здесь достаточно append-only release/audit ledger плюс обычная relational business model. Microsoft Learn

17. Projection — что это такое
Publication уже знает:
что означает анализ.
Projection отвечает:
как этот результат показать конкретному consumer.
То есть:
Canonical Publication
       ↓
Projection
       ├─ Overview
       ├─ Funnel
       ├─ Stock
       ├─ Advertising
       ├─ Categories
       ├─ SKU
       ├─ Actions Snapshot
       └─ Chat Context
Это очень похоже на materialized read model: источник истины остаётся отдельно, а view оптимизируется под конкретный способ чтения и может быть пересобран. Именно это является одним из стандартных преимуществ CQRS/materialized-view подхода. Microsoft Learn

18. Projection не является новым source of truth
Например Overview показывает:
Продажи −12%.
Эта цифра не должна жить только в:
overview_projection.revenue_delta
Source:
Factual Universe
Projection лишь подготовила значение к отображению.
Если projection потеряли:
rebuild
из:
Publication
+
sealed factual universe
+
projector version
Microsoft прямо описывает materialized view как производное представление, которое можно полностью восстановить из источника и которое приложение не должно изменять напрямую. Microsoft Learn

19. Projection полностью deterministic
Никакого:
Publication
↓
ещё один OpenAI call
↓
Dashboard
Нет.
Projector:
pure deterministic application code.

20. Что Projector имеет право делать
Он может:
выбрать Findings для нужной страницы;
сохранить их Deep ordinal;
сгруппировать Actions;
подставить labels;
подготовить карточку;
сформировать URL entity;
считать UI-safe delta из двух готовых facts;
форматировать Money;
форматировать Percent;
показать unavailable/partial state;

21. Что Projector не имеет права делать
Нельзя:

создать Finding;

создать Recommendation;

создать Action;

повысить priority;

решить, что проблема critical;

придумать forecast;

исправить Deep output.
То есть:
Deep:
что это значит

Projector:
как это показать

22. Projector не должен semantic-rank Findings заново

Finding 1
Finding 2
Finding 3
...
Если Overview помещает максимум 5:
берём первые 5,
которые относятся к допустимому Overview scope.
Не строим второй ML/score/rule engine:
severity × GMV × recency.

27. Projection не должна читать LATEST
Когда строится Projection исторической Publication #108:

Иначе 22 августа мы пересоберём UI 20 августа уже на других данных.
Это недопустимо.

28. Publication coherence — крайне важное правило
Это напрямую исправляет старую проблему Aivion:
AI говорит одно, а цифры на карточке рядом уже другие.
Если Finding сформирован на:
Sales current_7d:
10–16 Aug

Stock snapshot:
17 Aug 05:00
то факты рядом с Finding должны соответствовать именно этому universe.
Нельзя показать Finding:
Stock = 0, необходимо пополнение.
а рядом тихо заменить карточку:
Stock = 180
из свежего snapshot 6 часов спустя.

49. Action Proposal vs Action Case

50. Action Case — долгоживущая сущность
На publish Action Proposal reconcile'ится с существующими Cases.
Например:
Publication 108
A17:
SKU417 replenish 120
       ↓
Action Case C31
На следующий день:
Publication 109
A9:
SKU417 replenish 150
       ↓
тот же Action Case C31
В Case:
proposal history:

20 Aug → 120
21 Aug → 150
Ничего не перезаписываем.

51. Case identity
После нашего multi-entity анализа identity должна быть:
seller
+
action_type_key
+
target
+
normalized_action_context
+
intent_signature
+
action_identity_version
Например:
seller=1
action=SKU_ADJUST_AD_BID
target=SKU417
context=Campaign58
intent=DECREASE

52. Почему action type version не всегда должен ломать Case
Если мы выпустили:
SKU_ADJUST_PRICE contract v1 → v2
но business semantics те же, это может оставаться тем же Case.
Поэтому identity лучше привязать к:
action_type_key
+
action_identity_version
а не ко всякому техническому schema patch.

53. Action reconciliation на publish
Для каждого validated Action Proposal:
Есть OPEN Case с тем же identity
→ REAFFIRM
→ добавить новый proposal
→ latest_proposal_ref обновляется
Нет Case
→ создать новый Action Case
Есть противоположный active intent
Например:
старый:
DECREASE_PRICE

новый:
INCREASE_PRICE
→ старый SUPERSEDED
→ новый Case
Backend не объединяет противоположные intents.

76. Почему Outbox
Если сделать:
COMMIT publication
↓
отправить Redis/event
и процесс упал между двумя шагами, cache/consumers могут не узнать о новой Publication.
Transactional Outbox решает именно проблему такого dual-write: состояние и event-intent фиксируются одной транзакцией, после чего отдельный relay доставляет событие; доставка обычно at-least-once, поэтому consumers должны быть idempotent. Это стандартный надёжный паттерн. Microsoft Learn
Для Aivion это можно реализовать достаточно просто поверх PostgreSQL + existing Worker, без новой тяжёлой инфраструктуры.

150. Publication Model — итоговый контракт
Я бы зафиксировал его так:
Publication Aivion является immutable release snapshot одного полностью завершённого Daily Analysis над одним sealed Factual Universe. Analysis Run является mutable orchestration entity и не становится Publication до успешного прохождения всех AI, validation, Action и required Projection stages. Частичная техническая Publication запрещена; partial/unavailable business capabilities являются допустимым содержимым полноценной Publication.
Publication фиксирует seller, analysis date/cutoff, factual universe, capabilities/DQ, exact analysis component references, canonical semantic result, validated Action Proposals, contract/version bundle, artifact hashes и projection manifests. Исторические provider revisions не переписывают опубликованные результаты.
Текущая Publication определяется отдельным per-seller atomic pointer. Standard publish не может заменить current более старым analysis date/cutoff. Same factual universe + same effective analysis contract не порождает новую Publication без явного reanalysis intent. Rollback/withdrawal изменяет control plane, но не содержимое Publication.
Publication Projection является deterministic, rebuildable read model над Canonical Publication и её sealed Factual Universe. Projector не вызывает AI/provider APIs, не создаёт новых Findings/Recommendations/Actions и не осуществляет semantic repair. UI redesign изменяет versioned Projector, а не AI contract.
Publication-linked analytical values обязаны сохранять temporal coherence с sealed universe. Более свежие operational facts могут предоставляться current UI только отдельным explicitly timestamped Latest Overlay и не заменяют factual basis опубликованных Findings/Recommendations/Actions.
Historical Publication Action Snapshot и mutable Current Action View являются разными read models. Publication сохраняет то, что Aivion рекомендовал на момент анализа; Current Actions отражает persistent Action Cases с пользовательскими DONE/DISMISSED состояниями и новейшими valid proposals. Action Groups остаются deterministic projections над atomic Action Cases/Proposals и не имеют собственного mutable lifecycle.
Publish выполняется атомарно относительно Publication record, Action Case reconciliation, current pointer и transactional outbox intent. Required immutable artifacts создаются и hash-валидируются до DB commit. Downstream cache/UI notifications работают at-least-once и idempotently.

Цель

96. Обновлённый архитектурный контракт
Я бы добавил в ТЗ следующий нормативный блок:
Каждая новая Daily Analysis generation обязана выполнить continuity revalidation всех atomic Action Proposals, представленных в предыдущей current Publication, независимо от их текущего пользовательского статуса. Действия предыдущей Publication не копируются в новую Publication автоматически. Каждое из них должно быть повторно подтверждено на новом sealed Factual Universe.
При первоначальном формировании Action Deep Analysis обязан выделить bounded набор REQUIRED_SUPPORT — семантических оснований Action, grounded на Findings и Fact Handles. Backend не определяет бизнес-основания самостоятельно. В следующей генерации Deep должен отдельно оценить актуальность каждого REQUIRED_SUPPORT на current factual context.
Предыдущий Action может быть reaffirmed и связан с тем же persistent Action Case только в случае FULLY_SUPPORTED, то есть когда все его REQUIRED_SUPPORT по-прежнему подтверждены. Изменение recommended parameters при неизменных основаниях не создаёт новый Case.
Если хотя бы одно REQUIRED_SUPPORT перестало быть актуальным, предыдущий Action не переносится в новую Publication как прежний occurrence. Если текущий Deep Analysis всё равно формирует аналогичное действие на ином наборе оснований, прежний occurrence закрывается, а новый Action Case occurrence создаётся немедленно.
При NOT_SUPPORTED Action отсутствует в новой Publication, соответствующий Action Case системно закрывается как NO_LONGER_RECOMMENDED, после чего применяется versioned Action Recurrence Policy. После завершения suppression period новый occurrence разрешён, если новый анализ снова обнаруживает достаточные основания.
При UNVERIFIABLE, когда из-за capability/DQ limitations невозможно подтвердить все обязательные основания, Action не отображается как актуальный в новой Publication, но Case не считается разрешённым и переводится в состояние ожидания повторной проверки. Recurrence cooldown в этом случае не применяется.
Пользовательский DONE закрывает только конкретный Action Case occurrence и не является доказательством исчезновения factual основания. Action из предыдущей Publication всё равно проходит следующую continuity revalidation; если основания сохраняются, Deep может немедленно сформировать новый occurrence того же Action.
Multi-entity Action Group не переоценивается как единое действие. Каждый atomic member переоценивается независимо. Новая Action Group строится детерминированно исключительно из текущих validated atomic Actions новой Publication. Поэтому изменение 4 SKU → 3 SKU является не изменением старой группы, а формированием нового immutable group snapshot из трёх reaffirmed/current Actions.
Continuity revalidation является обязательной частью двухэтапного AI pipeline, но не создаёт третий AI-вызов. Current context для предыдущих Actions подготавливается Evidence Expansion через closed CONTINUITY_REQUIRED recipes, а итоговая semantic revalidation выполняется существующим Deep Analysis call.
Количество публикуемых atomic Actions должно быть ограничено таким образом, чтобы архитектура гарантировала возможность полной переоценки Actions предыдущей генерации в следующем run. Непроверенное действие не может считаться сохранённым или разрешённым.
Что я считаю особенно важным
Твоя формулировка фактически меняет философию Actions в лучшую сторону:
Action
не живёт сам по себе между генерациями.
Живёт:
Action Case history.
А актуальность Action каждый раз должна быть доказана заново.
Поэтому current Actions — это не список накопленных задач:
вчера AI что-то придумал
→ висит до ручного закрытия.
А:
новая генерация
→ заново проверили факты
→ заново подтвердили основания
→ показали только то,
  что актуально сейчас.
Именно такую модель я бы считал правильной для Aivion.
Остаётся один реальный продуктовый вопрос, который этот алгоритм не закрывает: что делать с DISMISSED / Отклонить. Для DONE ты уже определил правило — оно ничего не suppress'ит. Для NO_LONGER_RECOMMENDED — системный временный cooldown. Для сознательного пользовательского DISMISSED я бы рекомендовал отдельный versioned suppression period, иначе пользователь сегодня нажмёт «Не хочу выполнять», а завтра получит ровно ту же рекомендацию. Но это решение лучше явно утвердить отдельно.
Да, фиксируем именно так.
Если менеджер нажимает «Неактуально / DISMISSED», то для этого конкретного действия запускается 30-дневный suppression period. В течение этих 30 дней такое же действие по той же сущности не показываем, даже если промежуточные генерации снова находят основания.
Например:
21 августа
SKU417
SKU_INCREASE_REPLENISHMENT
→ менеджер нажал «Неактуально»

21 августа – 19 сентября
такое же действие не отображаем

20 сентября и далее
если новая генерация снова подтверждает основания
→ создаём новый Action Case occurrence
→ действие снова показывается
При этом suppression относится именно к той же business action identity:
seller
+
action_type
+
target
+
normalized context
+
intent
Поэтому если менеджер отклонил:
SKU417
ADJUST_PRICE
intent = DECREASE
это не должно блокировать, например:
SKU417
INCREASE_REPLENISHMENT
или противоположное:
SKU417
ADJUST_PRICE
intent = INCREASE
если текущий анализ реально пришёл уже к другому управленческому решению.
Для групповых действий всё остаётся атомарным. Если пользователь на группе:
Пополнить 4 товара
нажимает «Неактуально для всех», backend фактически делает DISMISSED для четырёх отдельных Action Cases:
SKU417 → suppressed 30d
SKU522 → suppressed 30d
SKU816 → suppressed 30d
SKU901 → suppressed 30d
Сама Action Group никакого собственного cooldown не получает.
Итого теперь lifecycle хорошо разделяется:
DONE
→ закрыли конкретный occurrence
→ никакого cooldown
→ если завтра действие снова обосновано,
  можем показать его снова

DISMISSED / НЕАКТУАЛЬНО
→ закрыли occurrence
→ same action suppressed 30 дней
→ после 30 дней можно снова показать,
  если основания есть

NO_LONGER_RECOMMENDED
→ система сама установила,
  что основания исчезли
→ также применяется recurrence suppression
  согласно принятой policy

SUPERSEDED
→ появилось другое/противоположное действие
→ новое можно показать сразу
То есть менеджер действительно может через месяц снова получить ту же рекомендацию и, если по его бизнес-контексту она всё ещё не нужна, снова нажать «Неактуально» ещё на 30 дней. Это понятное и предсказуемое поведение.
